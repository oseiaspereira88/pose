# POSE — Project Operating Standard for Engineering

## 1) What it is

POSE is the operating standard for agent work in **{{PROJECT_NAME}}**.

Primary goals:

- reduce ambiguity in tasks
- improve execution predictability
- make validation and reporting consistent
- scale collaboration in a heterogeneous repository

POSE does **not** replace product architecture or existing security policies;
it organizes how agents execute technical work.

The short agent contract lives in [`AGENTS.md`](AGENTS.md); this document is
the operating manual (structure, CLI, per-type flows, CI, governance).

---

## 2) Principles

1. **Scope first**: read only the instructions and artifacts needed for the affected directories.
2. **Plan before implementing**: non-trivial changes go through a spec/plan.
3. **Incrementalism**: small, cohesive, auditable deliveries.
4. **Deterministic validation**: prefer reproducible commands (`test`, `lint`, `typecheck`, `build`, contract/security checks).
5. **Risk transparency**: always surface gaps and human-review points.

- Subproject `AGENTS.md` (when present): local guidance, applied only to that directory's scope.
- [`.pose/workflows/*.md`](.pose/workflows/): procedure per work type (`feature`, `bugfix`, `review`, `refactor`, `documentation-update`, `recurrence-escalation`).

- [`.pose/templates/spec.md`](.pose/templates/spec.md): the single per-feature spec template.
- `.pose/project.json`: the project's declared identity, `{"schema_version":1,"project_id":"proj.<name>","name":"…"}`, written by `pose install` and seeded by `pose update` from the id an older instance declared in `.mcp.json` or `AGENTS.md`. Resolution reads `POSE_DEFAULT_PROJECT_ID`, then a `POSE_PROJECT_ROOTS` binding, then this file, then the directory name; a binding that disagrees with the file is refused as `conflicting-project-binding`, a malformed file as `invalid-project-id`, and `pose doctor` reports both under `project.identity`. Declared once, the id is the same in every checkout, under any directory name, for the CLI and the MCP server.
- [`.pose/templates/roadmap.md`](.pose/templates/roadmap.md): governed roadmap template.
- [`.pose/templates/changelog-fragment.md`](.pose/templates/changelog-fragment.md): user-facing fragment per spec (written at closeout).
- [`.pose/workflows/release.md`](.pose/workflows/release.md): immutable release preparation, publication reconciliation and verification.

Release cuts use `pose release plan`, `prepare`, `check`, `notes`, `record`,
`status`, `open-next` and `backfill`. A tag is not publication; terminal release
confidence comes only from provider and independent-verification evidence.
- [`.pose/templates/doc-audit-report.md`](.pose/templates/doc-audit-report.md): template for editorial reviews and documentation audits.
- `pose` binary: native scaffold/check/validate/report automation and MCP server.
- [`.pose/specs/*/spec.md`](.pose/specs/): living specs per feature.
- Native project-state artifact, generated by `pose state init` (`pose state`/`pose_project_state`) — optional, absent on a freshly-installed project; configurable staleness policy (optional, defaults 7 days / 20 commits — see §6).
- [`.agents/skills/`](.agents/skills/): 11 skills in Codex-native format (`name`/`description` frontmatter, body with Required reading + Steps + Output requirements, optional metadata in `agents/openai.yaml`). Use `description` as the single routing source; Claude Code consumes the symlinks in [`.claude/skills/`](.claude/skills/) without requiring `when_to_use`.

### 5.1 Spec lifecycle

Every spec created by `pose new-spec`
carries frontmatter with state and dates, preventing specs that linger "open"
after completion and follow-ups that rot into dead text.

```yaml
---
slug: <feature-slug>
status: draft        # draft → in-progress → done | blocked | superseded | abandoned
created_at: 2026-01-15   # stamped by pose new-spec
completed_at:            # filled on the transition to done
supersedes:              # slug of the superseded spec (when applicable)
depends_on:              # prerequisites: other-spec, milestone:<roadmap>/<id>, roadmap:<slug>
priority:                # integer >= 0 (lower = higher priority)
---
```

- **`status`** evolves `draft` → `in-progress` → `done`. Alternative terminal
  states: `superseded` (use `supersedes:` on the successor) and `abandoned`.
  `blocked` is not terminal: it is an operational condition a spec can leave.
  Readiness keeps a blocked spec not ready, still resolves its `depends_on`
  and reports `cause: dependency` or `cause: unknown`; spec transfer also uses
  `blocked` while a destination is staged. It is never a delivery outcome, and
  no command rewrites a legacy `blocked` spec to `in-progress`.
- **`created_at`/`completed_at`** give the spec's real time window (file mtime
  is unreliable — it changes on every edit).
- **`depends_on`** declares prerequisites as an **inline comma-separated
  list** (POSE frontmatter is flat by contract — never a multi-line YAML
  list), with typed refs: a spec slug, `milestone:<roadmap>/<id>` or
  `roadmap:<slug>`. Spec refs are resolved by `check` (existence + graph
  acyclicity); `milestone:`/`roadmap:` refs resolve against the governed
  roadmaps in `.pose/roadmaps/` when they exist. `depends_on` expresses a real
  technical/logical prerequisite; scheduling preference is `priority`'s job.
  The aggregated graph lives in
  [`.pose/indexes/spec-graph.json`](.pose/indexes/) (generated by
  `pose index`; frontmatter stays authoritative) and a spec's eligibility is
  queryable via the pose-mcp tool `pose_spec_readiness`.
- **`priority`** (optional) orders attack preference among eligible specs; it
  creates no blocking.
- **Follow-ups with disposition:** the `Final Report > Follow-ups` section is
  not free text. Each item gets a bracketed disposition — `[open]`,
  `[spawned: <slug>]`, `[covered: <slug>]`, `[duplicate: <slug>]`, `[done]`,
  `[wont-do: <reason>]`. That answers, per follow-up, whether it seeded a new
  spec, is already covered elsewhere, was triaged before, or was discarded.
  Open items additionally declare ownership and a triage service level with a
  trailing `(owner:@alias crit:low|medium|high review:YYYY-MM-DD)` group —
  the SLA is a triage promise, not an implementation deadline. That group is
  the only format read: it must be the last thing on the bullet, in
  parentheses, and the bullet may wrap. Ownership written any other way is
  ignored, so the item reads as `unowned` and never becomes overdue;
  `pose lint-spec` warns about it. Legacy items without the group are reported
  as `unowned` (warning at closeout).
- **Requirement trace:** at closeout, the `Validation > Requirement trace`
  subsection maps every declared `R<N>` to its outcome — `[satisfied]` with
  evidence (free text plus structured refs `check:`, `test:`, `report:`,
  `commit:`), `[waived: <reason>]` or `[withdrawn: <reason>]`. Orphaned or
  missing IDs fail `lint-spec --strict`; the MCP tool
  `pose_requirement_trace` exposes the bidirectional projection. A `test:` ref
  must name a test that exists in the repository, its submodules or a nested
  module repository the validation matrix registers: a Go test function or
  subtest, a JavaScript/TypeScript test title (exact or in slug form), a Python
  `test_` or Rust `#[test]` function, a tracked test file, or a `go test -run`
  pattern that selects a test. An unresolved ref fails `lint-spec` and
  `pose close` while the spec is open, and is only reported on a closed spec.

Closeout is an explicit step (skill [`pose-spec-closeout`](.agents/skills/pose-spec-closeout/SKILL.md)):
set `status: done`, fill `completed_at`, triage every follow-up and pass the
gate `pose lint-spec <slug> --strict`,
which blocks "done without `completed_at`" and "done with an undispositioned
follow-up". The aggregated live backlog (`pose followups --open`) feeds the
planning of new specs.

Follow-up triage has **two layers**, by design, to keep the CLI deterministic
and avoid cascading drift:

1. **Deterministic (CLI):** `pose followups`
   proposes near-duplicate candidates by lexical similarity. Reproducible, no
   network, runs in CI.
2. **Semantic + confirmation (agent):** the `pose-spec-closeout` skill judges
   intent equivalence (what lexical heuristics miss) and **confirms with the
   user before writing** the consequential dispositions
   (`[spawned]`/`[covered]`/`[duplicate]`) — reusing a follow-up is a
   decision, not a default.

### Command reference

- `init` — ensures the minimal required `.pose` directory structure, policy files and indexes. Supports `--wizard` to auto-detect repository stacks and seed the initial validation matrix.
- `check` — validates POSE structural integrity (required paths and references in `AGENTS.md`/`POSE.md`) **plus** the [`validation-matrix.json`](.pose/indexes/validation-matrix.json) schema, [`task-map.json`](.pose/indexes/task-map.json) sync, the native spec dependency graph and the schema-version gate. It fails in `--strict` and warns where permitted in `--tolerant`.
- `specs` — lists and discovers repository specifications sorted chronologically (newest first). Supports `--recent <N>`, `--status <status>`, `--since <duration|date>`, `--components <tags>`, and `--json`. An unknown flag, a missing value, an unparseable, negative or out-of-range `--since` and a non-positive `--recent` exit 2 before anything is listed (spec `pose-cli-mcp-operation-results`); a bare `--recent` means 10. `specs facts <slug>` takes `--json` in any position and refuses anything else. MCP `pose_list_specs` refuses the same values, an unknown argument, an explicit `0` for `recent` or `limit`, an explicit `null` and a `sort` other than `date` or `slug`. With `--json`, an operational failure of `specs`, `specs facts`, `start` or `close --plan` is one operation result with outcome `failed` and a typed cause, exit 1.
- `spec-format` — inspects and migrates specifications to the modern chronological date-prefixed format (`migrate <slug>|--all [--format folder|flat] [--dry-run]`, `status`). Enforces mandatory directory envelope preservation whenever companion artifacts (`amendments.jsonl`) exist.
- `spec-transfer` — explicit cross-project authority transfer. `preview` emits a deterministic digest-bound JSON plan without writing. Requirement mappings are explicit (`R1=equivalent:R1`, `R2=withdrawn`, `-=pending:R3`); apply requires the same digest plus one `--authorize-project` for every affected repository, and resume verifies the saved plan copies and receipts. Transfer is refused until both endpoints and every affected project adopt review-policy schema 4 (`qualified_artifact_refs_version: 1`, `spec_authority_transfer_version: 1`). Current dependency/membership links follow the verified redirect; the MCP tool `pose_spec_transfer_status` reads the journal only within its authorized project. `--mode reconcile-terminal` retires a coordinator spec onto an executor that is already `done` with a terminal closeout in its own project: the executor file is never written (apply only verifies its digest), the map is N:M over every source requirement and may target another spec with `destination_ref`, `withdrawn` needs a `rationale`, and `pending` needs a `rationale` plus an open target spec, recorded in the schema-2 redirect as `open_obligations`; `--map-file` reads the map as JSON. Engines without this mode refuse schema-2 plans and redirects. No automatic commits, pushes or policy adoption occur. Split-section specs without a single `spec.md` are reported as unsupported rather than rewritten.
- `new-spec` — creates a new spec with standard lifecycle frontmatter and 7 engineering sections. By default writes the dated flat file `.pose/specs/YYYY-MM-DD-<slug>.md`; `--folder` writes `YYYY-MM-DD-<slug>/spec.md` and `--legacy` writes `<slug>/spec.md`, all under [`.pose/specs/`](.pose/specs/).
- `new-adr` — creates an ADR with the standard template and a deterministic slug.
- `new-roadmap` — creates a governed roadmap from [`.pose/templates/roadmap.md`](.pose/templates/roadmap.md): flat frontmatter (`status: draft|active|done|abandoned`, `depends_on:` between roadmaps) + milestones as `## Milestone: <id>` sections with flat bullets (`- after:`, `- target_start:`, `- target_due:`, `- specs:`). `check` validates single membership in active roadmaps, milestone/roadmap DAGs, dates and typed-ref resolution; `pose_spec_readiness` resolves those refs for real (milestone satisfied = its specs done; roadmap satisfied = status done). Dates are planning input; actuals derive from events.
- `new-knowledge` — creates an artifact in [`.pose/knowledge/`](.pose/knowledge/) from [`.pose/templates/knowledge.md`](.pose/templates/knowledge.md) with mandatory frontmatter (`type`, `owner`, `sensitivity`, `created_at`, `last_reviewed_at`, `expires_at`). Computes `expires_at` from the TTL (default 30d, max 90d).
- `validate` — runs the declarative matrix in [`validation-matrix.json`](.pose/indexes/validation-matrix.json): per-stack checks, per-module overrides, severity (`required`/`optional`) and mode (`strict`/`tolerant`). `--json-out`/`--junit`/`--sarif <path>` (`--json <path>` still works as a deprecated alias of `--json-out <path>`) emit the versioned structured result (schema 1) from one canonical model: stable check IDs (`<module>/<stack>/<name>`), command metadata, timing, severity, distinguishable outcomes (`pass|fail|error|skipped` — infra failures never masquerade as check failures), deterministic skip reasons, bounded captured output and secret redaction (configured env values only; inherited environment never enters the result). Text output stays authoritative; machine formats are additive. POSE-specific semantics survive the JUnit/SARIF projections via documented extensions (classname suffix / `pose/*` properties).
  **Runtime guardrails:** every check runs under a timeout (`timeoutSeconds` per check, `defaults.timeoutSeconds`, safe default 600s) and an output ceiling (`defaults.maxOutputBytes`, default 1 MiB); breaching either terminates the process group and records the explicit state (`limit_state: timeout|output-limit`). Checks marked `isolation: "required"` never run locally — they are skipped with a machine-readable reason and exported by `--emit-plan <file>`: an execution-plan envelope binding project, spec, check plan, matrix digest, git HEAD and an approval slot to be stamped with an expiring execution identity before the Harness may run it.
  **Changed scope:** `--changed-from <rev> [--changed-to <rev>]` selects the minimum safe module set deterministically — modules containing changed files (tracked and untracked), transitive dependents via `dependsOn` edges in [`module-metadata.json`](.pose/indexes/module-metadata.json), and policy widening (criticality `high` always runs). A change outside every module runs everything (uncertainty prefers safe execution); unselected checks are recorded as skipped with the selection reason and `--explain` prints every decision. Revisions are confined to a safe grammar; without the flags, full validation is unchanged.
  **Evidence classes:** every check declares the `evidenceClass` it produces from one closed vocabulary — `build`, `unit`, `integration`, `e2e`, `reachability`, `a11y`, `design-system`, `contrast`, `visual-regression`, `lint`, `typecheck`, `security-scan`, `contract` — the same vocabulary review profiles may demand; a check outside it is refused, and a check with no class contributes nothing when a review collects evidence. `--report` writes a report listing the commands this run executed and its result, and derives the outcome from them.
- `update` — single-command complete update: automatically checks and updates the `pose` binary executable to the latest GitHub release, refreshes scaffolds, rules, workflows and MCP config (`--force`), and migrates the repository instance schema (`.pose/schema-version`). A plain update merges `POSE.md`/`AGENTS.md` (instance-owned sections keep their content; an instance edit a merge cannot keep is saved to `<file>.pose-backup`, and a section that still matches what POSE last wrote is simply replaced), delivers machinery — backing up only files the instance edited since POSE delivered them, as recorded by digest in `.pose/state/machinery-manifest.json` — and seeds absent instance config; `--force` additionally reruns `install` over the instance, which resets the manuals wholesale. Use `--dry-run` to preview or `--no-self` to skip the binary self-update. A run that delivered its files but finds the instance's own state invalid reports that through the final gate and does not roll back. Downgrade is always refused.
- `index` — generates `repo-map.json`, `services.json`, `packages.json`, `spec-graph.json` and `roadmaps.json` (the specs' `depends_on`/`priority` graph, cached for pose-mcp) in `.pose/indexes/`, including per-module operational metadata from [`module-metadata.json`](.pose/indexes/module-metadata.json).
- `report` — generates a versionable report in `.pose/reports/` with execution metadata, minimal per-task history (`.pose/reports/history/`) and stable-field diffs.
- `knowledge-check` — double gate: (1) validates each artifact's frontmatter in [`.pose/knowledge/`](.pose/knowledge/) against the rule (`type`, `sensitivity`, `expires_at`, TTL ≤ 90d), and (2) counts the overdue backlog against `--max-overdue`. In `--strict` both gates exit 1.
- `recurrence-check` — scans [`history JSONL`](.pose/reports/) for `task_slug`s with `≥ --threshold` occurrences in `--window-days` (default 3 in 14d). Ignores `outcome=pass` by default (problematic recurrence is repeated failure), but a `pass` settles the earlier failures of its own `stable_hash` cluster: only failures after a cluster's latest `pass`, or with no `pass` in the window, count, and a pass of another `stable_hash` settles nothing. Settled clusters are not flagged and are listed as `resolved` findings with `recurrence.resolved_clusters`; `--include-pass` counts every record as before. A task whose consecutive runs switch between passing and not passing at least `--flap-threshold` times in the window (default 4) is reported as a `flapping` warning with `recurrence.flapping_keys` (spec `pose-recurrence-flapping-signal`); it never changes the exit code, because an unstable outcome is a signal to investigate, not a recurrence. When flagged, points to [`recurrence-escalation.md`](.pose/workflows/recurrence-escalation.md).
- `recurrence-effect` — closes the feedback edge: `--register` ties an escalation to its intervention (`rule:|workflow:|spec:<name>`) and observation window in append-only `interventions.jsonl`; the report compares recurrence rate (and optional `pose report --duration-seconds/--cost-usd` telemetry) before/after per intervention with data-quality warnings (sparse sample, incomplete window). `INEFFECTIVE` verdicts demand a governed follow-up; `--fail-ineffective` makes that blocking by policy. Aggregation is by task/context only — never individuals.
- `extension install|list|remove|verify` — signed extension lifecycle (spec pose-extension-catalog-lifecycle): a package is a directory with `extension.json` (id, version, kind: `skill|workflow|rule|import-adapter`, `pose_schema_range`, `files`, `permissions`, optional `conflicts_with`, `provenance`) plus `files/<repo-relative-target>` for every declared path. Targets are confined to `.agents/skills/`, `.pose/workflows/`, `.pose/rules/`, `.pose/templates/` and must fall inside the package's own declared `permissions`. Extensions are **data only** — the lifecycle never executes anything from a package. `install`/`remove` are dry-runnable (`--dry-run`), require explicit consent (`--yes`) and are transactional: any mid-transaction failure rolls back every file already written. A conflicting target (owned by another extension, or an existing untracked file) blocks the operation unless `--force`; a locally modified managed file blocks `remove` unless `--force` (user modifications are preserved by default). Unsigned packages are rejected unless `--allow-unsigned` is passed explicitly; signature verification runs `cosign verify-blob` against the identity the package's own `provenance.signer`/`provenance.issuer` declare. Installed extensions are recorded in `.pose/indexes/extensions.lock.json` (id, version, per-file digest, provenance, signature status) — read-only over MCP via `pose_extension_list`; `install`/`remove` stay CLI-only by design (POSE never exposes general-purpose write tools over MCP). A `revoked: true` manifest is always rejected.
- `skills-check` — Agent Skills conformance gate (spec pose-agent-skills-conformance): every `.agents/skills/<slug>/SKILL.md` must declare `name` (matching its directory), `description`, `when_to_use` plus POSE's additive compatibility metadata `pose_schema_range` (`"min-max"` against `.pose/schema-version`), `clients` and `capabilities` (comma-separated). Every relative markdown link must resolve inside the repository (no path escape); content is scanned offline for unsafe instructions (`curl | sh`-style, `--no-verify`, disabled TLS verification) and secret-shaped strings (defense in depth, not a replacement for the dedicated secret-scanning gate). Declaring the `claude-code` client requires a real `.claude/skills` symlink in `scaffold.ClaudeSkillLinks`. `--strict`/`--tolerant` mirror `check`.
- `lint-spec` — verifies each `spec.md` section has real content, not placeholders. **`--ready-check`** applies the **Definition of Ready** (ENTRY gate): Intent/Requirements/Technical Plan filled, acceptance criteria with stable IDs (`- R<N>:`) and syntactically valid `depends_on` — without requiring Validation/Final Report. The Definition of Ready is opt-in: it applies to specs created on or after `adopted_at` in `.pose/policy/dor.json` (shipped empty), and `task_type` in the spec's frontmatter selects which sections it requires; once adopted, `check` applies it on the `→ in-progress` transition. Use `--all` to audit every spec; `--required-only` skips the optional `Decisions` section. **Lifecycle gate:** `status: done` requires `completed_at` and a valid disposition on every follow-up; for `spawned`/`covered`/`duplicate` the target must be an **existing** spec (and not itself). A target in another project is written qualified, `[covered: xref:<project>/spec:<slug>]`: when that project is bound (`POSE_PROJECT_ROOTS`) the spec must exist there, and when it is not bound the target is accepted, because the other repository being absent is not evidence the spec is missing. In any status it warns when an open follow-up's ownership is written outside the trailing `(owner:@alias crit:low|medium|high review:YYYY-MM-DD)` group, and it reads a wrapped follow-up bullet as one item, like `followups`.
- `followups` — aggregates all specs' follow-ups, derives the live (`--open`) or full (`--all`) backlog, projects ownership (`--owner <alias>`) and expired reviews (`--overdue`), and proposes near-duplicate candidates by deterministic lexical similarity (token Jaccard + `SequenceMatcher`, stdlib only; threshold via `--similarity 0..100`, default 60). Exit 0 by default, no network; `--fail-overdue` turns expired reviews into a blocking, risk-based policy gate. The candidates are mechanical hints — the **semantic judgement** and the **confirmation of reuse** live in the agent layer (skill `pose-spec-closeout`), never in this script. Source coverage (spec `pose-source-coverage-integrity`): the read reports what it could not see. `--json` carries `coverage_complete` and `coverage` (each loss names the artifact, the kind, and the spec it belongs to when the file name or a readable header shows it), the human output prints `coverage=INCOMPLETE` and each unread file, and `--fail-overdue` fails instead of certifying "none overdue" over an incomplete read. The backlog, `--candidates`, the project state and `pose state --attention` count one unresolved set: an explicit `[open]` and a bullet with no disposition (Attention projects the latter as `followup-undisposed`). The same applies to `pose assess tech-debt`, whose report states the files scanned, the ones it could not read (incomplete) and the ones it leaves out on purpose (over the size limit, binary, generated), and finds a marker after a very long line; and to the review history: `pose review-check` and `pose review verify` do not take the latest readable attempt or attestation as the current one while an unreadable record that may be later exists, and `pose review record` refuses to choose the attempt it supersedes from a history with a hole. The obligation report marks a producer `incomplete` when it lost an element (an obligation refused by validation, a spec or review record it could not read).
- `review-plan` / `review-check` / `closeout-check` — resolve a deterministic component-aware plan from governed metadata, typed overlays and a closed native-tool catalog, then validate immutable attempts against both scope and plan digests. Opt in explicitly with review-policy schema v2, `component_aware: true` and `component_aware_adopted_at`; preview the migration read-only with `pose review-plan <scope> --explain` before committing the policy. Completed attempts older than that component adoption date remain auditable, while open scopes require the new plan. `pose review record` is dry-run by default, accepts `--plan-digest` to reject drift and appends with `--apply`; recommended tools are never executed implicitly. Hierarchical closeout rolls approvals through `spec:`, `milestone:` and `roadmap:` scopes. Read-only MCP: `pose_review_plan`, `pose_closeout_state`. The JSON of `closeout-check` and `pose_closeout_state` types its blockers in `diagnostics` (code, domain, refs, satisfaction condition; text blockers the engine cannot type yet are carried as `opaque`) and its next action in `next_step`; readiness `waiting_on` entries carry a `code`, and auto-attest pendencies a `code`, `source` and `condition` (spec `pose-typed-producer-diagnostics`). The prose fields stay for people; consumers read the codes.
- `review bundle` / `review attest` / `review auto-attest` / `review verify` / `review record` — opt-in fixed-point review (`review_bundles: true` plus an adoption date). Evaluation is a DAG, and each stage names the one before it: the implementation subject carries an `implementation_digest` over its classified content alone — not over change-set ids or refs, so a squash or rebase of the same content keeps its identity — and an observer of the implementation anchors there rather than on the bundle that will contain it. Sealed evidence records `subject_observation` as `observed`, `carried-forward` or `unknown`; a result naming no commit is unknown, never current. A change set's range observation reports how many commits `base..head` spans against how many it attributes, because paths resolved from trailers are attributed while the range between them is only provenance; it sits outside the sealed payload, so an unrelated commit never stales a review of content that did not move. A criterion is `mechanical` when it names evidence classes a registered check emits, and `judgment` otherwise: `auto-attest` answers the first kind from the sealed evidence and reports the second as pending, refusing `--apply` until a reviewer records a conclusion for each. A profile may declare `kind` explicitly to ask for judgment on a criterion a check also covers; it may not declare `mechanical` on one naming no evidence class. A component-scoped tool whose component the validation matrix declares runs no check (`replaceDefaultChecks` with an empty list) is planned with `producer_coverage: none` and may be disposed `not-used` with a reason, because nothing in the repository can emit what it asks for; everywhere else a required tool must still pass. Preparation hashes the semantic Intent, Requirements, Technical Plan and Decisions, attributed patch/tree content, consumed plan inputs, validation identities and child bundles. Tasks, execution logs, Final Report, lifecycle metadata, attestations and derived state remain outside the review digest but retain their own gates. `--seal` persists immutable JSON in the review-bundles directory under an `rvb-` identity; attestations are separate append-only JSON in review-attestations under an `rva-` identity. `auto-attest` extracts matching evidence from validation results and resolves tool dispositions deterministically. Semantic or source changes create a superseding bundle and typed delta; derived closeout changes do not cause rereview. Local review stays offline. Conductor may return an optional Ed25519 envelope only when its issuer/public-key pin is trusted by policy. Human plan output groups repeated path warnings and separates active required, recommended and completion-deferred tools; JSON retains full provenance. Sealing also records the governance contracts in force (`component-aware`, `review-bundles`, `evidence-vocabulary`) and the gates that decide the bundle (reservations, accepted-risk severities, criterion reuse); verification reads them from the bundle, and only `require_signed_attestations` is read live. Sealing warns about evidence produced against a commit other than the approved head. Sealing also records the implementation identity: principal, vendor, model, a digest of the sealing session's reference (never the reference) and whether it was `detected` from the session's agent markers or `declared` with `--seal --lead <vendor>[/<model>]`. The model comes from `--lead` or `routing.lead_models` and is `unknown` otherwise, which never establishes a model difference; markers of two vendors leave the vendor `unknown`. Resealing content a sealed bundle already holds returns that bundle with the identity it recorded, so a reviewer closing out never becomes the implementation; only a `--lead` naming another identity seals anew. The identity is sealed but is not content: a sealed bundle matches a preparation that differs from it only by the identity. An attestation's `passed` criterion must cite evidence the bundle contains, of a class the criterion accepts (any one of its `evidence_classes`), from the component it is about — evidence from a directory inside a component does not answer for the component. `--criterion ID|disposition|evidence|rationale` records `passed`, `not-applicable` (rationale required) or `finding` (names a recorded finding); `--finding ID|severity|disposition|action|evidence[|owner|rationale|review-by]` needs a severity and an action, and `accepted-risk` or `wont-fix` needs a sealed accepted severity, an owner, a rationale and a review date. Read-only MCP: `pose_review_bundle`. `pose_review_prepare` (read-only) returns the auto-attest draft and its pending judgment criteria; `pose_review_attest` (spec `pose-mcp-review-attest-signed-only`, `governance-write`) records an attestation over MCP only inside a trusted issuer's envelope, the proof `--envelope` verifies; its preview completes a draft for a sealed bundle (bundle digest, attested time, id and, when it names `confirmed_by`, the confirmation digest) and returns the exact bytes to sign. A human confirmation is disclosed as verified only when the signed authority claim names that human.
- `close` — applies a review-gated lifecycle transition to complete a spec, milestone, or roadmap. The transition is published only over the bytes its gates judged, under the spec's lifecycle lock that start and transfer also take (spec `pose-writer-coordination-and-atomic-publication`): an edit made while the gates ran is a `publish-conflict` that keeps the edit, the authorization is judged again inside the lock, and a start or transfer holding the spec refuses the close with the lock's owner (`start-in-progress` or `spec-lifecycle-in-progress`). Git state (spec `pose-git-and-dispatch-snapshot-integrity`): a `git status`, HEAD or tree that cannot be read is unknown, not clean — the close plan blocks on it rather than sealing evidence over a working tree it could not see (a directory with no repository at all is a different fact and keeps its behaviour); the governed snapshot, the review-bundle path check and the obligation snapshot report an unreadable status as unknown too. `review dispatch` compares the review worktree with the sealed commit's own tree before and after the run, so `assume-unchanged`, `skip-worktree`, a replaced type or a link cannot hide an edit; native derived regeneration requires exact producer outputs that remain regular files; adapter output belongs on stdout or the external output path, and directory names grant no permission to modify the review worktree, and a run that finishes after its bundle was superseded or its policy changed is recorded `stale`, history and not the scope's current fulfilment.
- `continuous-closeout` — persists and projects continuous closeout terminal state for rapid-iteration workflows. `status --json` writes one operation result whose `data` holds `active` and `terminal`; the exit stays 1 while an active scope is not terminal.
- **Output channels** — the result (verdict, findings, data) goes to stdout and progress (steps, usage, the command's own failures) to stderr, so `pose x --json | jq` is safe and `2>/dev/null` never hides a finding. `--json` prints one document whose finding `severity` is the untranslated anchor; `--quiet` prints the verdict alone; `pose validate --verbose` streams a check's output instead of capturing it. Colour, symbols and the spinner exist only on a terminal, resolved per stream, and honour `--color`, `POSE_COLOR`, `NO_COLOR` and `TERM`; `COLUMNS` sets the wrap width and `POSE_LOCALE` (`en` or `pt-BR`) the language of every message POSE composes. Exit codes: 0 pass, 1 gate failure, 2 usage error.
- `artifact-check` — parses exact `### Artifacts` actions, resolves an explicit base/head range or `POSE-Spec: <slug>` commit trailers with safe structured Git arguments, and reports resolvability, existence, action mismatch, undeclared and orphan findings. A claim on a changelog fragment that `pose release prepare` archived resolves through the release manifest, which records the fragment's spec and digest; prepare never edits a spec. Commits modifying artifacts declared by a spec must carry a `POSE-Spec: <slug>` trailer in their commit message for `artifact-check` and `pose close` to attribute the changes. `pose report --change-from/--change-to` persists immutable change-set evidence; `pose index` projects claims, observations, reverse provenance and findings into `delivery-integrity.json`. The seven files `pose index` writes are one generation (spec `pose-index-generation-integrity`): their bytes are written under `generations/<id>/` in the indexes directory, the legacy names are published from the same bytes, and the descriptor `generation.json` there — SHA-256 of each file plus the digests of the inputs they were computed from — is published last and is the commit. A reader fixes the generation the descriptor names and checks each file against it: a set that does not verify (a file missing, replaced, from another generation, or a descriptor it cannot read) is `unavailable`, with the reason, never an empty or mixed result; a repository that never ran `pose index` since this contract keeps working and is reported `legacy-unversioned`, with no claim of coherence. A generated index edited by hand has no effect while the generation's copy exists (readers read the generation), and in a clone without the copy it makes the set unavailable; either way `pose index --verify` names the file. `pose index --verify` reads without writing and exits 1 unless the set is current, the legacy names are those of the generation and its inputs (specs, roadmaps, policy, module metadata, validation matrix) still hold. A failed publication leaves the previous generation in force and a retry converges on the same identity; publishers hold a generation lock in the indexes directory (it never waits: a second `pose index` is refused with `index-generation-busy` and writes nothing, and a lock whose holder is proven dead is recovered), the first publication of a repository is marked pending so one that did not commit reads as `unavailable` and not as a mixture of two runs, an operation that reads several indexes (the review plan) fixes one generation for all of them, and a commit whose durability could not be confirmed is reported as committed; retention keeps the current generation and the newest others up to three, never anything younger than ten minutes, and a retention failure is a warning, not a failed publication. Limits: Git history is read by the delivery graph but not pinned by the descriptor, and a clone without the git-ignored `generations/` directory verifies the legacy names against the descriptor. MCP: `pose_delivery_integrity`.
- `artifact-backfill` — proposes explicit historical provenance from Git history (`--from-git`) and requires `--confirm-spec-edits` before applying unambiguous proposals to spec artifact claims.
- `surface-check` / `roadmap-check` — extend the same graph with typed `delivers` refs, production entrypoints, closed validation `evidenceClass` values and provenance-bound structured results. Surface profiles require reachability plus integration/e2e; composed capabilities require integration. Roadmap criteria may reference only registered delivery refs, checks or confined manual-review reports—raw commands are rejected. MCP: `pose_surface_assurance`.
- `state` (spec `pose-project-state-artifact`) — native project-state artifact: answers "what is the current state of this project?" in one read instead of scanning specs/roadmaps/follow-ups/capabilities/knowledge/reports every session. `curated` sections (executive summary, current direction — human prose, preserved verbatim) and `derived` sections (specs & roadmaps, follow-ups, capabilities, decisions & knowledge, validation & evidence, architecture — counts and typed pointers, never copied content). `init` scaffolds; `refresh` recomputes derived sections while preserving curated ones, stamping `generated_at`/`baseline_commit`, and publishes only over the state it read, so a curated edit made while it renders is a `publish-conflict`, never overwritten; a refresh that published the state and could not append its history says so (`state.published=`, refresh log `result: partial`), and the next refresh appends its own entry, while `pose state` reports it as `history-not-appended` (spec `pose-writer-coordination-and-atomic-publication`); `--if-stale` only redoes the work when the artifact is already `stale` (cheap to run on every CI build). With no subcommand, validates schema, staleness (age/commits since the last refresh, configurable policy), **per-section hash** — a hand-edited derived section fails nominally (`[TAMPERED]`) — and `refresh_pending` (see below). `diff` compares the last two refreshes. MCP equivalent: `pose_project_state` (`section` param fetches just one). Additive: a project without the artifact generated yet stays valid everywhere. The Architecture section reports `unavailable` in this version — no local GraphForge export producer exists yet.
- `state --governance [--scope <ref>] [--json]` (spec `pose-effective-governance-projection`) — live, read-only projection of what governance is in force here: for each registry contract, optional capability (atomic start, contract nodes, causality closeout, qualified references, spec transfer, criterion reuse, signed attestations, verified identity) and gate (Definition of Ready, delivery integrity), whether it is `supported`, `configured`, `applicable` and `effective`, with reason codes such as `not-adopted`, `no-readiness-cutoff`, `legacy-cutoff:<date>` or `identity-assurance-declared`. `--scope` compares the scope's newest sealed bundle — the contracts it stamped — with what the policy seals today. It reads the same functions the gates call and writes nothing. `pose_project_state` carries the same projection as `effective_governance` (optional `governance_scope`).
- `state --attention` (specs `pose-obligation-projection`, `pose-state-attention`) — live, read-only answer to "what is still owed, by whom, restricting which phase?". Obligations are projected from the subsystems that own them — readiness (unmet `depends_on`, Definition of Ready, unexplained `blocked`), closeout and review of in-progress specs (an unapproved review, each judgment criterion a sealed bundle still owes, text blockers carried as `legacy-opaque`), start reconciliation when atomic start is adopted, and open follow-ups as advisory residual debt — never stored a second time. Project-level sources are projected too (spec `pose-attention-projects-every-source`), originating on `xref:<project>/project:<project>`: an open docs review mark (owed by the doc's owner until `pose docs-review resolve`), a capability mechanism with a stale trigger, a release newer than the newest verified one that is not yet verified, and an accepted-risk or follow-up finding past its review date in the latest legacy review record. Free-form investigation notes carry no state and are not a source. The render shows coverage first: a producer that failed, or action requests until adopted, makes the answer `INCOMPLETE`, so an empty group never reads as nothing owed, and a fresh install, once committed, reads `complete`. Then what needs `--actor` (or any person or role), then what restricts each phase (`start`, `execution`, `review`, `closeout`, `release`), then residual debt. `--json` returns the report — stable `obl-` ids, qualified refs, reason codes, conditions, recipients, effects, satisfaction, knowledge, waiting, a snapshot of revision/dirty tree/policy/contract/index digests, per-producer coverage — plus the `attention` grouping. MCP: `pose_obligations` returns the same ids from the same function. Attention is not a gate.
- `action <open|list|show|resolve|cancel|waive|invalidate>` (specs `pose-action-requests`, `pose-action-request-resolution`) — material requests to a person or an external system that no other source records: a decision, an approval, an input, an external operation or an acceptance, with its question, options and consequences, recommendation, recipient (principal, role or `unassigned`), qualified targets (`requirement:R4` inside the origin spec, or `xref:…`), per-phase effects (`--effect closeout:block` lets implementation continue) and an optional subject (`--subject requirement:R4` or `path:<file>`) whose change invalidates an answer recorded for the old content. Open one only when a different answer would materially change execution, scope, authority, risk acceptance, closeout or publication and no authorization already given covers it. Each request is an append-only journal under `.pose/actions/`, read whole: a line with a second value, a duplicate field (keys differing only in case included), an unknown event type, another schema, a sequence gap, an empty line or no terminator is never part of a view; `action show|list` and MCP locate it (line, byte offset, length, SHA-256) as an `interrupted-tail`, with a truncation proposal for a person to review, or as `corrupt`, to restore from version control — the engine repairs nothing (spec `pose-journal-checkpoint-and-lock-recovery`); `open` is a preview until `--apply`. Targets are qualified with the current project id; when it is derived from the directory name (no `.pose/project.json`, `POSE_DEFAULT_PROJECT_ID` or `POSE_PROJECT_ROOTS` binding), `open --apply` says so (on stderr with `--json`), because a checkout under another name would record another project, and the obligation snapshot lists the same limitation. A resolution names the `--request-digest` it answers and the `--expected-revision` it read, carries an `--idempotency-key` (a retry is a no-op, the same key with other content is refused, a second answer against the same revision is refused) and comes from an actor holding the recipient role in `.pose/policy/actions.json` (`{"schema_version":1,"roles":{"maintainer":["human:<name>"]},"identity_assurance":"declared|verified"}`); under `verified` it needs `--claim <file>` with an Ed25519 claim from an issuer pinned in the review policy, bound to project, audience, request digest, principal and answer (a human principal also needs `human_authority_issuers`). Answered is not satisfied: a declined approval, a rejected acceptance or a failed external operation leaves the condition unmet. The requester may cancel its own question; a waiver needs the recipient authority and a reason. Open requests are projected as `actor-action` obligations in `state --attention` and `pose_obligations`; MCP opens requests with `pose_action_open` (risk class `governance-write`, a preview unless `apply` is true) and reads them with `pose_action_requests`; `pose_action_resolve` (spec `pose-mcp-action-resolve-signed-only`, `governance-write`) records an answer only with the principal's proof — a signature by a key registered to it, or a trusted issuer's claim — and refuses a declared answer under any assurance; its preview returns the statement to sign and the `ssh-keygen` command.
- Action destination scoping (spec `pose-action-target-and-node-scoping`) — origin is provenance, targets select relevance, and effects select restrictions. An empty effect scope still means the whole source artifact; a roadmap or milestone expands its current members. Explicit scopes replace that default, so a request from alpha can restrict beta without blocking alpha. A named whole artifact is a whole restriction, not partial merely because it is qualified. Pending requests remain visible when their origin becomes terminal. Unknown membership or unreadable material is reported as limited coverage and never expands into every spec. CLI accepts `--effect-json '{"phase":"start","mode":"block","scope":["xref:project/spec:beta"]}'`; MCP `effects` accepts the same object alongside legacy `"start:block"` strings. Targets and subjects resolve by project/artifact/kind/ID, and a subject is re-read in its recorded artifact. Under adopted agency readiness, new approvals and acceptances require an explicit `--subject` / `subject`; legacy unbound requests retain their journal and report that answers have no content-change detection. Policy-off creation and transition defaults remain unchanged. This compatibility tightening requires release review; no policy adoption happens here.
- Signed answers (spec `pose-signed-action-answers`) — a principal proves an answer with an SSH key the project registered, with no external service. `pose identity add [<principal>] --key <file.pub> [--role <role>] --apply` records the key under `keys` in `.pose/policy/actions.json` (only `ssh-ed25519` and `sk-ssh-ed25519@openssh.com`; a key belongs to one principal; a private key file is refused); without a principal it suggests `human:<name>` from the git identity, which is a name, not a proof. `pose identity list [--json]` shows principals, roles and fingerprints; `pose identity remove <principal> [--fingerprint <fp>] --apply` stops future answers by a key without touching roles or answers already recorded. `pose action resolve … --sign <private key>` signs with the user's own `ssh-keygen -Y sign -n pose-action-answer` (POSE never reads the key); `--signature <file>` attaches a signature made elsewhere over the exact bytes `pose action statement <act-id> --actor <p> --answer <a> --idempotency-key <k>` prints, which bind project, request id and digest, actor, answer and idempotency key. POSE verifies the SSHSIG natively, records statement, signature and key on the answer, and `pose action show` verifies it again from the journal. A signed answer is `verified` under any assurance; under `identity_assurance: verified` an answer needs a registered key's signature or a trusted issuer's claim — two emitters of identity proof, Harne8 being one issuer. Presence follows the explicit channel contract below. `pose doctor` (`actions.keys`) warns when a human role holder under verified assurance can prove no answer, or signs only with keys that cannot prove presence (an error under `require_presence`).
- Policy scope validation (spec `pose-policy-scope-validation`) — `identity_assurance` and `reviewer_independence` accept only exact `spec`, `milestone` and `roadmap` keys in every supported review-policy schema, including disabled configuration. Empty keys, typos, whitespace, case variants and future kinds are refused with the field, quoted key and supported kinds; no key is normalized and no operator file is repaired automatically. Unknown top-level metadata remains permitted. This stricter refusal is breaking and requires major-release classification, without automatic migration or adoption. Current preparation, `state --governance` and MCP `pose_project_state` report invalid policy explicitly; no partial projection advertises protection. A protected Git baseline with an invalid selector stops new preparation instead of falling back to an unprotected warning. Global governance entries describe instance configuration and name the protected kinds; `--scope`/`governance_scope` adds historical bundle context, not per-scope capability evaluation. Malformed context selectors are refused. Historical sealed records and their stamped gates remain readable and unchanged; inability to evaluate current policy is not a retrospective invalidation of those records.
- Human presence (spec `pose-proof-presence-channel-parity`) — preserve roles and keys when explicitly migrating `.pose/policy/actions.json` to `schema_version: 2`. Presence defaults to disabled; when `require_presence: true`, choose `presence_scope: "universal"` or `"sshsig"`. Universal requires a registered SK signature with an authenticated user-present assertion for every human answer, including issuer-backed answers. SSHSIG scope requires it when an SSH signature is supplied; issuer-only answers are explicitly outside that scope and establish no presence. An issuer claim may accompany an SK signature, but every supplied proof must verify. Identity grants, Portal authentication and user-verification alone are not presence. Agents do not acquire human-presence assurance. Enabled schema-1 policy requires migration before new human answers; unknown scopes are refused and older engines reject schema 2. This is a breaking change, requiring major-release classification, without automatic policy adoption. Previews disclose current policy as not-evaluated and never request a touch. Historical reads reverify recorded proof, disclose the key's assertion separately from identity, and leave historical presence requirements unrecorded; they never impose today's scope retrospectively. A verified assertion does not attest hardware provenance or who touched the key.
- Guided setup (spec `pose-setup-command`) — `pose setup` shows, in one place, the project identity, principals and keys (with the principal the git identity suggests, which is a name and not a proof), the pre-commit gate, capabilities in force, capabilities new since the last configuration review, what needs setup, whether the configuration is committed, and one next step with its command. At a terminal it offers each open step — the hook, registering a key with the `maintainer` role, each new capability (adopt, decline or defer with a reason) — and performs it only after an explicit yes; with `--json`, `--no-input` or no terminal it changes nothing. New means off, undecided and introduced after `reviewed_version` in `.pose/policy/adoption-decisions.json` (every off, undecided capability when none is recorded); a fresh install records its engine version, deciding the last new capability advances it, and a deferral is asked again under a newer engine. `pose install` ends with `pose setup` as the next step, `pose update` names the pending decisions instead of "Nothing to do", and `pose doctor` reports them as a `next` step (`setup.capabilities`).
- Onboarding spec (spec `pose-onboarding-spec`) — a new instance starts with a governed first spec, `.pose/specs/<date>-pose-onboarding.md` (draft, in the install's locale): adopting POSE is the project's first piece of work, with requirements for the declared identity, a maintainer able to prove answers, the commit gate, the reviewed capability defaults and the committed instance, tasks that point to `pose setup`, a decision recording the defaults, and checks (`pose doctor`, `pose check --strict`). It passes lint, the strict check and the Definition of Ready as written. `pose setup` names `pose start spec:pose-onboarding` first and, once every other step is done, `pose close spec:pose-onboarding`. Only an install that creates the instance writes it; `pose update` and a reinstall never create or overwrite it.
- Configuration review (spec `pose-update-configuration-review`) — when `pose update` finds capabilities this project has not decided for the engine it runs, it writes `.pose/specs/<date>-pose-configuration-review-<version>.md` (draft, one requirement per capability with its effect, version and recommendation) and opens one decision request per capability (`adopt`, `decline`, `defer`; `adopt` recommended for a capability new instances get), addressed to the `maintainer` role and restricting only the review spec's closeout. Nothing is adopted by the update. The maintainer answers with `pose action resolve` (signed when the policy asks, or over MCP with `pose_action_resolve`) or at a `pose setup` prompt; `pose adopt --request <act-id> [--apply]` applies an answered request — adopt turns the capability on dated that day, decline and defer record the decision with the answer's reason and the request id — and refuses an open, cancelled or foreign request. A second update for the same version asks nothing again; `pose setup` lists open review requests with the resolve command and answered ones not yet applied.
- Phase readiness (spec `pose-phase-scoped-readiness`) — `pose_spec_readiness` with `phases: true`, and `state --attention --scope spec:<slug>`, report per phase (`start`, `execution`, `review`, `closeout`, `release`) whether it is `clear`, `restricted`, `partially-restricted` on named nodes or `unknown`. A phase is `clear` only when no obligation restricts it and every producer that could restrict it was read; a restriction on `R4` alone is reported as partial with the note that independence of the rest is not demonstrated. `ready` keeps its legacy meaning: partial eligibility never turns it true.
- Governed capabilities (spec `pose-governed-capabilities-default-on-new-instances`) — agency readiness, contract nodes, atomic start and causality closeout with the `structural-materiality@1` overlay. A new instance adopts all four: when `pose install` creates `.pose/policy/review.json` it sets their keys, dates atomic start, causality closeout and the overlay with the install day, and logs each adoption. An instance that already has a review policy adopts nothing at install, and `pose update` never adopts, even when it seeds a missing policy. `pose adopt <capability>` previews the keys one capability needs and `--apply` writes them, dated today or `--date YYYY-MM-DD`, so work created before the date is not re-judged; adopting an adopted capability keeps its date, `--off` removes the same keys, and a result the review-policy reader would refuse is never written. `state --governance` names the command for each capability not adopted. Every adoptable capability is in one catalog (spec `pose-capability-catalog`): the four above, criterion reuse, the Definition of Ready, the review overlays (`overlay:<profile>`), qualified references and spec authority transfer (which raise `schema_version` as their contract requires), signed attestations and verified identity. `pose adopt --list` shows each with its state — `on`, `off`, `declined`, `deferred` or `needs-setup` —, what it changes day to day, since which version and whether a new instance gets it (`--json` for the same data); a new instance adopts every capability the catalog marks as a default, the Definition of Ready and criterion reuse included. A capability whose requirement is off, or whose prerequisite (a trusted issuer, an authority audience) is missing, is refused with what is missing; `--off` is refused while another adopted capability depends on it. `pose adopt <capability> --decline --reason <text>` or `--defer --reason <text>` records in `.pose/policy/adoption-decisions.json` that the project looked and chose not to adopt it now, so it is not asked again; adopting later clears it, and the file is never shipped to another instance. A new instance's role map in `.pose/policy/actions.json` names nobody, and `pose doctor` lists naming them as a next step. A fresh install reports no warning in `pose doctor`: milestone and roadmap profiles count only once the project has a roadmap, and evidence-class coverage reads only the required checks of the shipped stacks some module uses (every shipped test and build check declares its class).
- Governed effects (spec `pose-governed-effect-enforcement`) — opt-in with `agency_readiness_version: 1` in `.pose/policy/review.json`. Once adopted, an unsatisfied action request refuses the transition it restricts at its write point: `pose close` refuses with `close.refused.action-request-pending` and the request's message, `closeout-check` / `pose_closeout_state` report the typed diagnostic and `next_step: answer-action-request`, continuous closeout cannot complete, `pose start --apply` refuses a plan restricted at start (a preview taken before a request was opened is stale at apply), and `pose release prepare` refuses — dry-run included — while a request restricts release of one of the release's specs. Each gate recomputes the restriction when it runs; a declined approval keeps refusing. Only action requests are enforced here: dependencies, review and evidence keep their own gates. Without adoption, requests are shown in Attention and restrict nothing, and `state --governance` reports the capability as supported and not adopted.
- Spec transfer and action requests (spec `pose-transfer-preserves-obligations`) — `spec-transfer preview` lists the source spec's action requests in `action_requests` with a disposition: `invalidate-in-source` for an open or answered request, `history-only` for one already closed. When the source is retired, each open or answered request receives an invalidation event keyed to the operation, so a resumed transfer records it once; a request opened after the preview makes the plan stale. Requests and answers are bound to their project and grant nothing in the destination, which re-opens a request if it still applies; a same slug and requirement id in two projects never share a request.
- `close spec:<slug> --plan|--apply|--resume` (spec `pose-recoverable-closeout-plan`) — the closeout as an ordered, recoverable plan computed from the repository: context (an in-progress spec, no uncommitted change outside the paths the plan writes), evidence and index (validate into `results_path`, then `pose index`, as a pair), seal, mechanical attestation (`--reviewer` names the reviewing execution; never invented), judgment, verify and the guarded transition. `--plan` previews (`--json` too); `--apply [--digest <plan digest>]` refuses a plan that no longer matches the repository, runs the mechanical steps and stops with exit 3 at a pending judgment, listing it with the sealed evidence refs (`closeout_plan.evidence`) and an attest command filled with them, one `--tool` per required tool and one `--criterion` per pending judgment (`closeout_plan.attest`, spec `pose-quickstart-real-lifecycle`); a requirement trace that is incomplete — a requirement with no entry, an orphan or malformed entry, or requirements with no `### Requirement trace` — blocks the plan at its `trace` step, before anything is sealed, and `pose close` refuses the transition for the same reason, so a closed spec never fails the lint that follows; `--resume` re-plans after an interruption, so done steps are not repeated and no bundle or attestation is duplicated. A checkpoint under `.pose/closeout-plans/` records progress and is removed on completion; a removal that fails is reported. It is progress, never a receipt (spec `pose-journal-checkpoint-and-lock-recovery`): `--plan` shows it as `valid`, `corrupt`, `unsupported` or `unavailable`; an apply over one that does not read stops before any step, for a person to inspect and remove it; and one that records an evidence, index, seal, attestation or transition step the repository does not reflect is a conflict, until `--apply --digest <current plan>` starts a new run. The plan never answers a judgment, publishes or edits policy, and promises a recoverable operation, not a transaction over Git and external processes. Operation results (spec `pose-cli-mcp-operation-results`, ADR 2026-10-16): `--apply|--resume --json` writes exactly one JSON document — `operation`, `outcome` (`completed`, `already-satisfied`, `waiting`, `blocked`, `conflict`, `failed`), the `step` it stopped at, `steps_run`, `pending`, `next_action`, the `effects` the domain confirmed, the steps left `unconfirmed` after a failure, `resumable`, a typed `error.cause` and the plan in `data` — and the human output reads the same result. A call that runs no step reports `already-satisfied`, not `closed`: it is not a fresh verification, and `pose closeout-check` is. Two different modes, or `--digest`, `--reviewer` or `--skip-evidence` with `--plan`, exit 2 before anything runs; `pose start` refuses two of `--apply`, `--status` and `--cancel`, `--digest` outside `--apply` and `--cancel --json`; an apply that fails after recording its baseline reports the recorded phase as a confirmed effect and the same `--apply --digest` as its next action, which finishes from the start record a transition already published; a spec that has not moved is judged again by the current plan and its governed restrictions, and a baseline the repository has moved past is reported as a conflict to cancel and preview again, never as resumable; a failed apply lists every state it confirms as an effect (the baseline and, once published, the spec moved to `in-progress`) and in `steps_run` only the steps that call ran, and a start record left unreadable (a baseline write cut short) is reported with the `baseline` step unconfirmed and a next action to inspect and remove it, never repaired automatically. `pose close <scope>` without a plan mode refuses `--json`. An MCP gate (`pose_check`, `pose_lint_spec`, `pose_skills_check`) stopped by its deadline or a cancellation returns `isError` with `error_code: execution_inconclusive`, its cause and partial output, never `passed=false`. The usage journal records a stop on a reviewer as `waiting`, not `failed`, and never averages an unmeasured interval as 0 ms.
- Reuse by material equivalence (spec `pose-material-equivalence-reuse`) — a criterion's answer is reused only when every input it depends on is equal in the new bundle: its definition, the independence, the scope sections, the subject entries (all of them for a subject-sensitive criterion), the evidence of the classes it accepts, the governing inputs and its tools; judgment reuse also needs `allow_criterion_reuse`. When a bundle is superseded, `review verify` (`delta.criterion_reuse` in JSON) shows each criterion as `equivalent`, `changed` with the inputs that changed, or `new`, and each reused answer names the attestation it came from. - Assessment freshness (spec `pose-adaptive-assessment-freshness`) — a component assessment records its binding: the committed tree of the component, the engine version and the validation-matrix digest. `pose assess discover --if-stale [--component <dir>]` reuses an assessment whose binding is unchanged and refreshes it otherwise, printing `assess.freshness.<component>` with the reason (content changed, engine changed, matrix changed, uncommitted changes, or no binding on an older record). - `followups --candidates [--json]` (spec `pose-followup-reconciliation-candidates`) — lists open follow-ups with a reconciliation reason: `target-terminal` (a spec the follow-up names is done, superseded or abandoned), `evidence-present` (a test it names now exists), `overdue` (its review date passed), plus lexical near-duplicate clusters. Each candidate shows its evidence and its limits; nothing is dispositioned, similarity never becomes `duplicate` without judgment, and an open follow-up never leaves Attention without a disposition written in its spec. - Progressive spec surface (spec `pose-progressive-spec-surface`) — `pose new-spec <slug> --surface minimal|standard|full` records `surface:` in the frontmatter. A `minimal` spec keeps Intent, Requirements, the Technical Plan with its Artifacts, Validation with the requirement trace and the Final Report with its follow-ups; it drops the planner-local Tasks section and the report subsections that `pose specs facts <slug> [--json]` derives from the delivery index (paths of the attributed commits, checks that produced scoped evidence). `lint-spec` stops requiring Tasks for a minimal spec and relaxes nothing else: the trace, follow-up and amendment gates apply as before. The facts never include intent, rationale or accepted risk. Evidence binding (spec `pose-spec-facts-evidence-binding`): `specs facts` separates `checks` (results whose scope provenance names the spec, with their basis and whether they ran against the head of the spec's change sets) from `candidates` (results the index holds that nothing ties to the spec: a declared module or an empty `components` is not provenance); candidates are printed as `CANDIDATE, not evidence of this spec`. `freshness` reports `fresh`, `stale` (an input changed since the index was published), `unknown` (never published as a set) or `unavailable`, and a limitation says to run `pose index` when it cannot be established; reading the facts never rebuilds the index and never concludes that a requirement is satisfied.
- **Automatic project-state refresh** (spec `pose-project-state-refresh-contract`) — an internal post-event hook registry fires a **partial** `pose state refresh` (only the sections an event affects) at the points POSE already intercepts: a successful `pose lint-spec <slug> --strict` on a `status: done` spec (`spec_closeout` → Specs & Roadmaps, Follow-ups, Validation & Evidence), `pose amend` (`spec_amend` → Specs & Roadmaps, Decisions & Knowledge), `pose reconcile-evidence record` (`evidence_reconciled` → Validation & Evidence) and `pose assess snapshot` (`assessment_snapshot` → Capabilities). When the event carries a commit and `POSE_GRAPHFORGE_MCP_URL` is configured, the consumer calls `components_hit` (spec `graphforge-components-hit-contract`) from the state's baseline to the event's commit and attaches the hit components to the Architecture section (**directed** refresh); without GraphForge configured, refresh stays full/undirected — zero build coupling. No daemon, no filesystem watcher: it is a synchronous call at the exact point each event already happens. **Best-effort by default**: a failed refresh never blocks the command that fired the event — it marks `refresh_pending: <event>` in the state frontmatter instead (cleared by the next successful refresh, regardless of trigger). Strict mode is opt-in via policy (`strict_refresh: true`) — there, a refresh failure fails the triggering command. Every run (triggered or manual) is logged to the artifact's own append-only log (metadata only: trigger, target, result `ok|failed|skipped`, duration, changed-section hashes — never content). Dedup key `hash(event+target+commit)`: the same event processed twice (retry/replay) does not repeat the refresh, result `skipped`; `manual`/`ci` refreshes are never deduped against each other (an explicit call always runs). `release_cut` is registered in the event→sections map but has no producer inside pose-mcp today — cutting a release belongs to Conductor (a separate service); the trigger is ready for when that integration exists.

Anti-noise threshold (`min_hits`, hit `level` `direct`/`any`, the demand's default owner/SLA) is configurable, sharing the same policy file already used for age/commit-based staleness (optional; absent means these same conservative defaults).

Deployments require `--deployment-kind planned|rework`; incidents require an environment; recovery includes only resolved `--caused-by-deployment` incidents. `adoption-metrics` aggregates specifications, roadmaps, and validation lifecycle rates.
- `stacks [--path dir] [--json]` — read-only, offline catalog inspection (spec pose-stack-catalog-expansion). Matches directory entries against the maintained profile catalog (Node.js, Go, Rust, Java, **Python** — poetry/pipenv/pip/setuptools/pep517 — and **.NET**), reporting per profile: manager, marker, `winner`/`shadowed` (multiple managers present resolve by declared priority), `confidence` (`medium` under conflict), and whether the prerequisite native tool is on `PATH` — via `exec.LookPath`, never by executing a project file. Detected markers feed `discoverValidationModules`/`pose init --wizard` the same way Node/Go/Rust/Java already do; the actual checks run through [`validation-matrix.json`](.pose/indexes/validation-matrix.json) `python`/`dotnet` stacks. Python manager priority is expressed with `when.fileNotExistsAny` (skip when any higher-priority lockfile/marker exists) alongside the existing `fileExists`/`fileNotExists` predicates.
- `assess discover|integrate|tech-debt|stale|request|snapshot` — native assessment engines for LOC, technical debt markers, component structures, inter-module contract integrity checks, and capability mechanism reassessment lifecycle.
- `doctor [--fix]` — environment, dependency, native runtime, and POSE instance health diagnostics, plus governance that would otherwise fail only downstream: `review.evidence-vocabulary` (a selected profile demands a class no check may emit), `validate.class-producers` (a criterion accepts only classes no registered check produces), `validate.evidence-class-coverage` (checks with no `evidenceClass`), `review.profile-schema`, `review.contract-adoption`, `review.scope-change-set`, and `<policy>.policy-keys` for nine policies (keys the engine does not read, i.e. a misspelled setting that silently does nothing).
- `knowledge-housekeeping` / `reports-housekeeping` / `events-housekeeping` — idempotent maintenance (list/archive/purge). Mutations require `--apply`. Reports housekeeping **never touches `history/`**: the JSONL is the source of truth for `recurrence-check` and `report`'s temporal comparisons. Defaults: stale = 120d, archive purge = 365d.
- `amend` — append-only spec amendment history (`amendments.jsonl` beside a folder spec's `spec.md`, or `YYYY-MM-DD-<slug>.amendments.jsonl` beside a flat dated spec; the spec is resolved through the store, so both layouts amend alike). `--baseline` snapshots every R-ID hash; `--ids R2 --change added|withdrawn|semantic|editorial --rationale <text> --author @alias [--reviewer @alias]` acknowledges a material change; `--list` renders history and pending acknowledgments. On `done` specs with a history, `lint-spec` rejects any requirement whose current text is not acknowledged by an event — specs cannot be silently rewritten after evidence. `--nodes [--json]` prints the versioned contract-node projection: requirements, assumptions and decisions with namespace, content hash, state and relations. With `contract_nodes_version: 1` adopted in the review policy, `--baseline` writes a schema-2 R/A/D snapshot, `--ids` accepts A/D, `--change transition` acknowledges an allowed state change, `editorial` is refused when a node changed state or relations, and the gate also rejects an active decision resting on an invalidated or withdrawn assumption. Without the capability the gate stays requirement-only and a schema-2 event is refused; schema-1 logs keep their meaning.
- `start` — atomic start of a draft spec, journaled in a per-spec start record. Without flags it is a read-only, digest-bound preview: readiness and dependencies, the declared review obligations (no future structural delta needed) and the R/A/D baseline. `--apply --digest <sha256>` records that baseline and moves the spec from `draft` to `in-progress` under a per-spec lock with compare-and-swap; it needs `atomic_start_version: 1` in the review policy, repeats idempotently, resumes an interrupted run and refuses another plan for a started spec. `--cancel` undoes a start that never moved the spec. The per-spec lock records its owner (host, digests of the machine and boot IDs, PID namespace, PID and process start); a lock another call holds is reported, never broken by age, as `owner-active`, `owner-unknown` or `owner-dead` (spec `pose-journal-checkpoint-and-lock-recovery`). Dead is proven only on the same Linux machine — another boot, or a PID that is not running or now belongs to another process — and `--recover-lock <owner digest>`, with the digest `--status` shows, removes that lock only if its bytes and its dead owner are unchanged, leaving the start record to resume; an unknown owner (another host, an older engine's empty lock, another platform) is checked and removed by a person. The same lock is the spec's lifecycle lock: close and transfer take it too, so no two of them interleave on one spec (spec `pose-writer-coordination-and-atomic-publication`). `--status` classifies each node as `recorded-before-managed-execution`, `introduced-during-execution` or `legacy-unbaselined`, recomputes obligations and, under the capability, asks for reconciliation when status or the recorded baseline was edited by hand. `atomic_start_adopted_at: YYYY-MM-DD` (spec `pose-atomic-start-adoption-cutoff`) limits the capability to specs created on or after that date: an older spec in progress without a start is reported as `legacy-unbaselined` with a note and blocks nothing; without the date every such spec needs reconciliation. A start records observable precedence, not when anything was decided; MCP exposes the read-only view as `pose_start_status`.
- `knowledge-usage` — projects `knowledge:<slug>` citations from specs per artifact (owner, expiry, citing specs). Usage signals inform the owner's review; TTL is never extended automatically. Dangling `knowledge:` refs fail `knowledge-check`.
- `knowledge-suggest <query>` / `semantic-suggest <query>` / `suggest-feedback` / `portfolio-projection` / `reconcile-evidence` — deterministic lexical ranking and advisory projections for knowledge, feedback clustering, multi-roadmap portfolio milestones, and delivery validation evidence reconciliation. Suggestions never gate or auto-apply without confirmation.
- `hooks` — links the native binary into `.git/hooks/`; invocation name selects `check --tolerant` for `pre-commit` and `index` for `post-merge`. `install --force` keeps a backup of pre-existing hooks.
- `version` — displays compiled Go binary version, commit SHA, and compares the repository schema version with engine requirements.
- `context` — resolves a selected logical project and optional local or `xref:`-qualified task through the shared artifact resolver. The JSON result includes canonical authority, project/artifact revisions, resolution state, supported contracts and a `context_revision`; it never includes filesystem roots. Use this token to detect a changed checkout or revision before a cross-project write.

Use `new-spec-qualified` for qualified creation so older engines reject the command itself. A project found only by `HARNE8_PROJECTS_DIR` scan can be read but does not grant write access. Existing canonical specs are reused; redirects and incomplete transfers block shadow creation.

- `contribute <enable|disable|status|stage|list>` — open-source contributor mode; stages sanitized reports under `.pose/contributions/` without leaking proprietary code; submission remains developer-adjudicated.
- `telemetry <enable|disable|status>` — manages anonymous, opt-in platform telemetry settings.
- `release` / `release-notes` — governed release lifecycle (`plan`, `prepare`, `check`, `notes`, `record`, `status`, `open-next`, `backfill`) ensuring immutable release notes, manifest freezing, provider evidence importing, and reproducible release verification. A release that introduces a governance contract carries a **Compatibility** section at the top of its notes, generated from the contract registry. `release-notes` provides a compatibility alias for viewing frozen notes. The version a cut is compared with comes from `version_source` in `.pose/policy/release.json` (`{"path": "VERSION", "kind": "text"}`, or `"kind": "json"` with a `key`): a project file holding `X.Y.Z`, with an optional `v` and `-dev` suffix. Only the engine repository may omit it; every other project must declare one. Manifest and tag integrity (spec `pose-release-manifest-tag-integrity`): a manifest is read through a strict contract (supported `schema_version`, no unknown fields, clean version and paths) that recomposes `specs`, `categories`, `breaking` and `release_input_digest` from the fragments it freezes, so an adulterated projection is refused instead of normalised. `check` and `status` verify a tag from its own tree: the tag (lightweight or annotated) is peeled to its commit, and the manifest, notes, frozen fragments and version source are read as blobs of that commit, never from the working tree. ## 7) CI policy

- Run `pose check --strict` on every `pull_request` to `main`; treat failure as blocking.
- Run `pose validate --strict` on every `pull_request` to `main`; treat `required` check failure as blocking.
- Run the same workflow on `push` to `main` to detect post-merge drift.
- Publish versionable artifacts per run: `pose-check.log`, `pose-validate.latest.log` and the `pose report` output.
- Consume those artifacts during review instead of ephemeral job logs.

A ready-made GitHub Action wrapping these gates ships with the POSE
distribution (`pose-action/`).

### Interpreting failures

- `POSE check (strict)` failure = structural break of the standard.
- `POSE validate (strict, required gate)` failure = objective quality block.
- `optional`-only failures = flagged technical risk; prioritize by criticality.

### Phased rollout (recommended)

1. Observability: PR workflow with artifacts, no new gates raised.
2. Enforcement on `main`: strict `check` and `validate` as blocking gates; adjust `moduleOverrides` for modules not ready.
3. Gradual expansion: promote mature checks from `optional` to `required` per domain.
4. Hardening: review the matrix periodically, remove temporary exceptions.

### Validation matrix per stack/module

- Single source: [`validation-matrix.json`](.pose/indexes/validation-matrix.json).
- Base stacks: `node`, `go`, `rust`, `java` (Maven/Gradle).
- `moduleOverrides` adjusts stack, mode and extra checks per module
  (`pose init --wizard` seeds them from repository scan).
- `required` in a `strict` or `tolerant` module → exit 1; `optional` failures don't block.

## Opt-in progressive review profiles (ABM)

Add `engineering-judgment@1` and/or `high-criticality-review@1` explicitly to
`overlay_profiles` in review policy schema v2 with component-aware review enabled.
Installation ships these profiles without activating them. Preview adoption with
`pose review-plan spec:<slug> --json --explain` in an isolated copy first.

Both profiles match declared surface, capability, contract, infrastructure or
governance delivery targets. The high-criticality profile additionally selects
`high` and `critical` explicitly and raises independence to `different-actor`;
an existing `mandatory-human` floor stays in force. They share three required
judgments: `assumption-integrity`, `design-causality`, `solution-proportionality`.
The last includes negative space and speculative extensibility. Matching both
profiles yields one instance of each judgment and adds no tools.

A target-free editorial scope receives no extra obligation, including in a high
component; a governance target with a Markdown entrypoint still matches. Missing
metadata remains diagnostic, not proof of low risk. See the authority contract
below for verified identities.

### Bands and the declared forecast

`review-plan` reports a `band` (`baseline`, `elevated`, `critical`) and one
`bands` entry per reason, each naming the `trigger` (the selector facts that
matched), the `basis` (`declared`, `observed`, `policy` or `unknown`), the
`source` where the fact is readable, the `policy` ref that made it consequential
and the `obligations` it produced. A criticality of `high`/`critical`, or a raise
of reviewer independence, makes an entry `critical`; another matched overlay makes
it `elevated`. An adopted overlay that could not decide a component — metadata
missing, or a selected field declared empty — yields a `band: unknown` entry with
no obligations: uncertainty is shown, never charged, and never read as low risk.

`projection` resolves the same plan over declared scope alone, labelled
`declared-forecast`. When delivery provenance attributes more scope than the spec
declared, `scope_expanded` is true and `observed_components`, `added_profiles`,
`added_criteria`, `added_tools`, `raised_independence` and `raised_band` say which
obligations only the observation produced. Each component also carries `origin`
(`declared`, `observed` or `declared+observed`).

Both are derived from the fields the plan already resolved, through the same
selectors and composer — there is no second policy engine — and neither enters
the plan digest. Publishing them therefore adds no obligation and supersedes no
sealed review.

### Observed structure and causal mapping

Declared metadata is the author's account of a change; it is a good first trigger
and a poor last one. Adopt `structural-materiality@1` and a profile also selects
on what the subject was observed to do, read from both sides of the sealed
subject. `structural_kinds` composes conjunctively with the other selectors, and
its vocabulary is closed to the kinds a detector can observe as material:
`dependency`, `component`, `delivery-metadata`, `governance-contract`,
`public-contract`, `submodule`.

Materiality is bounded on purpose. A transitive dependency, a lock file, a rename
and an unreadable manifest are all observed and all reported, and none is
material: the first two are consequences rather than decisions, a `component`
whose action is `changed` only restates the manifest edit beside it, and an
unknown reading is uncertainty, which `structure.unknown` shows and never charges.
The validation matrix is read by check: a change that only appends checks under
names the matrix did not carry is reported as one `validation-check` fact per
check and not charged, because registering a check strengthens what runs; any
other change to the matrix, including an added check that reuses an existing
name, stays a material `delivery-metadata` fact.
Each path is compared over what the scope's own commits did to it, not over the
subject's `base..head`: a range spans every commit between the first and the last
attributed one, so its diff also carries what other specs and releases changed in
between. The sealed subject records, per path, the blobs at the ends of each
uninterrupted run of attributed commits (`subject.attribution`), which keeps the
reading content-addressed. A run that includes a commit whose `POSE-Spec:`
trailers also name other specs cannot be split by commit; its facts carry
`shared_with`, and the plan warns that the reviewer should map the fact if this
scope made the change, or answer its mapping `not-applicable` with the reason.
A bundle sealed before this, or where Git cannot answer, is compared over its
range as before, and `range_observations` says whether that range is contaminated.
Nothing is resolved at all unless an adopted profile selects on structure, so a
repository that did not opt in pays nothing, not even the Git reads.

Unlike the band summary, the material set enters the plan digest: a criterion that
answers for observed structure owes one answer per fact, so gaining a fact makes a
sealed review stale instead of silently owing more.

A criterion declaring `requires_structural_mapping` carries that obligation, and
the profile — not the engine — says which one. Under the `structural-causality`
contract, passing it requires one `mappings` entry per material fact: either a
`basis` naming a requirement or constraint, or an assumption or decision that
reaches one, or an explicit `missing-evidence`, `not-applicable` or
`accepted-risk` with a rationale. Those three are kept apart because "we have no
evidence yet", "this does not apply" and "we accept this risk" are three
statements a single blank used to hide. Record them with
`pose review attest --mapping <criterion>|<delta>|<basis-or-disposition>|<why>`.
An approving attestation that verify would reject is refused before it is
written, and the refusal lives in the domain writer every channel shares: the
Store, `pose review attest` (preview, `--apply`, `--sign` and `--envelope`),
`pose review auto-attest --apply` and the MCP `pose_review_attest` tool all get
the same typed refusal, with each reason the verifier gives, and the attempt
writes no attestation, bundle, supplement or event. The writer completes the
canonical identity first, judges the bundle's sealed gates plus the live
signing and trust requirements and the time of the new operation, and refuses
the approval of a bundle that a newer seal superseded or that no longer
represents the current inputs. A trusted signature over invalid criteria still
verifies its identity, but is never written as an approval; the MCP preview of
an envelope returns `verify_blockers` and a refused apply returns
`error_code: review_approval_refused`. A `changes-requested` or `rejected`
attestation is an audit record: it is written without meeting the approval bar,
and still needs the proof its channel requires. Records persisted before this
are judged as they are, never rewritten.

The engine checks the namespace, the existence and the reach to a requirement —
pointing at a decision that reaches nothing states a choice without the
requirement that pays for it — and never checks whether the causal claim is true.
That is the reviewer's judgment. Disposing the criterion `not-applicable` while
the subject carries material facts is refused: an observed structural change is
not inapplicable, it is unmapped. Bundles sealed before the contract existed never
list it and keep their verdict.

Adopting `causality_closeout_version: 1` in the review policy stamps a further
contract, `causality-closeout`, on new bundles and seals the band and the
contract-node digest of each spec in scope, so a material R/A/D change makes the
review stale. Under it a mapping to an invalidated or withdrawn assumption, or to
a withdrawn decision, is refused; a `mapped` answer needs its own rationale, and
one reason pasted across three or more facts on the same basis is refused as
disproportionate; `accepted-risk` needs an owner and a review date
(`--mapping <criterion>|<delta>|accepted-risk|<why>|@owner|YYYY-MM-DD`) and never
waives a public or governance contract; `not-applicable` is refused while
structural coverage is unknown; and an elevated or critical band with material
facts but no criterion answering for them is refused, without requiring a human
reviewer. Bundles sealed without the stamp keep their verdict.

Adoption can be dated so it applies to the work that starts after it.
`causality_closeout_adopted_at: YYYY-MM-DD` stamps the contract only on a scope
with a spec created on or after the date; a scope whose specs are all older is
sealed without it and the bundle says why. `overlay_adopted_at` does the same per
overlay — `{"structural-materiality@1": "YYYY-MM-DD"}` — so adopting an overlay
does not charge its criteria, or a structural mapping, to work already under way;
a skipped overlay is named in the plan's explain trail and costs no Git read. A
spec without a creation date is never exempted, and an undated overlay applies to
every scope it selects.

### Protected policy baseline

A diff that changes the review contract cannot be the authority that approves
itself. When the reviewed scope touches `.pose/policy/` or `.pose/review-profiles/`,
the obligations are resolved a second time from the contract
as it stood at the change set's resolved base, and whatever the diff weakened is
restored for that review: the stricter reviewer independence, a criterion the diff
dropped (re-added with a `protected-baseline:` provenance), and a criterion the
diff softened from required to optional or from judged to collected. Restoration
is one-directional, so a baseline weaker than the diff changes nothing. Those
two directories are the contract — policy and profiles carry their own schema
versions — while rule bodies stay outside the gate, because it is the criterion
contract that is compared.

`policy_baseline` reports `protected`, the `revision`, the contract `paths`, the
`weakened` contract changes observed — including `allow_approved_with_reservations`,
`require_signed_attestations`, `identity_assurance` and `component_aware` — and the
`restored` obligations. A contract change whose base revision cannot be resolved is
reported unprotected, with a warning and an `unknown` band: POSE states that the
review is unprotected rather than implying it was protected.

Two cases used to make a contract change unreviewable, and no longer do: a diff
that sets `enabled: false`, and a diff that removes or breaks the profile the
policy points at. Both now resolve the plan from the protected contract and record
the weakening. Adopting a weaker contract stays possible; approving it under the
weaker contract does not. Restorations reach the plan digest through the criteria,
the independence and the explain trail, so a protected plan has its own identity.

## Verified review authority (ABM)

When a review policy sets `identity_assurance` to `verified` for a scope kind,
`agent:`/`human:` prefixes remain labels only. The attestation must carry a
`ReviewAuthorityClaim` signed by a trusted Ed25519 envelope, bound to the exact
bundle digest, project audience, reviewer principal and executions required by
the review plan. A human role also needs a dedicated authority grant. Existing
bundles without this sealed gate remain auditable in `declared` mode; POSE does
not infer cognitive independence or require Harne8 for offline review.

A claim carries two bindings, both read from the protected review policy and
never from the environment. `project` must equal `authority_project`, the project
id the decision governs; `audience` must equal `authority_audience`, the verifier
installation the claim is addressed to. One installation can serve several
projects, so the audience alone would let a claim issued for one of them satisfy
another; verified assurance therefore requires both keys, and each mismatch is
refused with its own reason. Action-request claims under `verified` follow the
same rule.

Every review surface discloses what its record proves. `review-plan` prints the
identity assurance in force; `review verify`, `review-check` and
`closeout-check` print one assurance line and carry an `assurance` object in
JSON with three separation readings kept apart: `separation_required` (the
plan), `separation_declared` (what the record's identity strings say) and
`separation_verified` (what a signed claim bound to the bundle established, or
`not-verified`). Under `declared`, `human:` and `agent:independent-` are shown
as declarations. `cognitive_independence` is always `not-observable`.

Attribution is recorded apart from identity. `pose review attest` accepts
`--prepared-by`, `--concluded-by`, `--confirmed-by` with
`--confirmation-mode adopted-conclusions|authorized-operation`, and
`--applied-by`; none of them is ever filled from `--reviewer`, and a
confirmation is bound to the digest of the exact decision, criteria, tools and
findings written. Adopting conclusions and authorizing an operation render
differently, and a confirmation is `verified` only when a verified authority
claim names that human. Records written before this carry no block and render
as `legacy-undifferentiated`. `pose review attribution-supplement` clarifies an
existing record by reference, append-only, and cannot add a confirmation.

### Historical review claims and criterion reuse

Review assurance discloses `temporal`: signed issuer-asserted `attested_at`,
claim validity at that historical time, current claim validity and current pin
trust. These fields never establish observed historical authorization. Expiry
is inclusive at equality, no TTL is imposed, and second-resolution historical
timestamps retain their bounded precision. New operations use their own time;
expired approving writes are refused before artifact creation. Current pins and
human grants remain the revocation boundary, including after key rotation.

`reused_from[].mode` can be `verified-source` or `current-reaffirmation`. The
former validates source proof, bundle bindings, sealed criteria, decision,
findings and recursive provenance. The latter records a current passed judgment
with a conclusion and keeps its source reference. An absent mode preserves
legacy behavior and is disclosed as `legacy-reaffirmation`, without a verified
historical-pass claim. Verify, review-check, closeout, CLI and MCP consume the
same domain result. Source traversal is operation-local: 16 levels, 32 distinct
attestations, 128 edges and 16 MiB of source files. A cycle, unreadable source or
exceeded budget is inconclusive and cannot satisfy verified-source.

This additive contract is classified for a minor release. It adopts no policy,
rewrites no historical record and creates no receipt retrospectively.

### Action lifecycle authority

An answer proof authorizes its answer only. New waiver, cancellation and supersession events carry `lifecycle_version: 1`. Under verified action policy they require an operation-bound SSHSIG (`pose-action-lifecycle`) or a trusted issuer's schema-2 action claim. MCP always requires this proof. Both supplied emitters must verify; human presence follows the current explicit channel scope.

Use `pose action waive` for a recipient/role authority's dispensation, and `pose action cancel` only to withdraw the requester's own question. Cancellation does not waive an independent producer's condition. With declared local policy, these operations remain declared and are disclosed as such. Unsigned legacy lifecycle events remain labeled legacy; they cannot dispense a condition under verified policy. Reads reverify signatures and issuer bindings at the recorded historical acceptance time, using current issuer trust pins. They do not prove historical role membership or hardware provenance.

Preview a lifecycle operation with the usual request digest, expected revision, idempotency key and reason. The JSON preview returns the exact statement. Sign it through `--sign` / `--signature`, or pass a schema-2 `--claim` file. Offline statements use `pose action statement <act-id> --operation waived|cancelled|superseded --actor <principal> --expected-revision <n> --idempotency-key <key> --reason <text>`. Supersession statements also need `--successor-id` and `--successor-digest` from the replacement preview. The signed claim binds `operation`, `expected_revision`, `idempotency_key`, `reason`, `successor_id` and `successor_digest`, in addition to the existing request/project/audience/principal/time fields; schema-1 answer claims cannot authorize retirement.

Preserve the preview's `requested_at` using `--requested-at` (CLI) or `requested_at` (MCP); it is validated as RFC3339 and keeps successor identity stable while signing. This timestamp is request metadata, not authenticated wall-clock provenance. Opening a replacement with `--supersedes` requires the predecessor's requester or recipient authority. With verified policy, pass `--authority <project-relative JSON>` containing actor, request_digest, expected_revision, idempotency_key, reason and signature or claim/envelope, plus the exact successor_id/successor_digest returned by the open preview. MCP `pose_action_open` accepts the same `authority` object, always with proof. Creation alone never grants authority to retire the predecessor. Authorization is checked before creation and again under the predecessor journal lock. An authorized replacement can be opened but not retire the predecessor if an intervening revision/policy change prevents the append; the error names the partial opening. Cross-journal recovery belongs to B10.

MCP `pose_action_resolve` defaults to `operation: answered`; `cancelled` and `waived` require a reason and return a lifecycle statement in preview. Arbitrary actor `invalidate` calls are refused. Subject-change invalidation is derived by the engine from the original and current material digests; transfer invalidation remains a governed engine path. These observations do not require a new human signature and never grant waiver authority. No policy, issuer or consumer pin is adopted automatically. The stricter authorization semantics require release compatibility review before publication.

### Action recovery and preflight

Preview `pose action resolve`, `cancel`, `waive` and replacement `open` through the same readonly domain admission as apply. Invalid actors, roles, options, request digests, revisions, projects and states are refused. Missing identity/presence proof is disclosed as `proof_pending: true` with `acceptance: not-certified`; no preview invokes a signer or certifies future acceptance. Apply repeats current authority, proof, state and revision checks under the journal lock. `pose action statement` checks answer admissibility before emitting bytes for an old material subject. An identical semantic idempotency key/payload records no second decision; a conflicting payload is refused. A renewed valid proof may acknowledge the same semantic decision without replacing its historical event.

`next_step` in request views, presentation, obligations, readiness restrictions and closeout diagnostics, and `next_steps` in Attention, distinguishes `answer`, `replace-request`, `repair-subject`, `remediate-or-waive`, `resume-supersession` and `repair`. These are instructions and requirements, never proof of authority or automatic effects. An invalidated request requires a materially updated replacement via `pose action open --supersedes`; missing material needs repair. Decline remains pending: remediate or obtain an authorized waiver with `pose action waive` / MCP `pose_action_resolve` (`operation: waived`). Repeating identical material with a new timestamp or lineage is refused. Material digests detect declared content changes; they do not judge whether rewritten text constitutes adequate semantic remediation. A satisfied answer is not asked again. Partial recovery offers the same prepared `open`, never an answer against an old digest.

Supersession reserves one immutable intent in `.pose/actions/supersessions/<predecessor>.json`. Preserve `requested_at`, predecessor revision/digest, successor ID/digest, retirement idempotency key, actor and reason for retry. `pose action open` / MCP `pose_action_open` resumes the same intent, checking current authority/proof before the remaining retirement. A competing intent is refused. The predecessor journal lock is nonblocking and held through reservation, successor creation and retirement; the writer takes no second journal lock and makes one attempt per call. Recovery phases are `reserved`, `successor-opened`, `complete` or `repair-required`; incomplete incoming/outgoing links stay restrictive. A successor cannot become a new predecessor before its incoming retirement completes. Both records remain visible until convergence. Completed retries acknowledge recorded history rather than applying another effect.

Intent files are regular, project-local, schema-checked and bounded to 64 KiB. A partial intent or journal requires explicit inspection/repair, including the missing identity/revision/material data; no command silently truncates, discards a reservation or retries forever. Lock contention and append/Sync errors retain the phase and original journals. Command refusal has `audit_persisted: false`: it is a diagnostic, not a journal `refused` event, and changes no legitimate question revision or idempotency history. Existing historical events remain readable. Upgrade all writers sharing the journals before adoption; older writers cannot enforce the intent reservation. This breaking behavior needs compatibility review before release; no policy, issuer or consumer pin is adopted.

### Amendment history before close

The first non-baseline `pose amend` on an empty history copies the valid completed atomic start baseline before recording the requested change. It uses the recorded hashes/state/relations, not edited text; the new baseline event records the current declared author/time, not past approval. Schema 1 keeps R nodes only; schema 2 requires `contract_nodes_version: 1`. An invalid or incomplete start refuses the append. No start means legacy behavior; an existing journal is never silently repaired. Explicit `--baseline` continues to snapshot the current state.

Amend and close share the per-spec lifecycle lock. The append writes baseline then change and calls Sync; failures are reported without truncating or rewriting history. A partial or malformed journal requires explicit inspection/repair. `lint-spec` warns about pending amendment findings on `in-progress` specs and rejects them on `done`; `pose close` checks the same history before transition and under lock. No history remains opt-out; no policy is adopted automatically.

### Terminal closeout verification

Lifecycle `done` records the transition; terminal verification reads the applicable review contract and current opted-in amendment/action/federation gates. `pose closeout-check`, `pose close --plan` and MCP `pose_closeout_state(include_plan=true)` share that verifier. A done plan exposes `lifecycle_done`, `verification` with `verification_basis` and `limitations`, and `next_action`; historical pipeline steps are `not-run`, not inferred as executed. `verify` reports the current query's verdict. Existing review cutoffs and sealed historical contracts remain applicable; a legacy exemption is disclosed without inventing an execution receipt.

For a done scope, `pose close --apply|--resume` is readonly: verified state returns `already-satisfied` with empty `steps_run` and `effects`, while missing required proof or invalid history returns blocked with a supported repair action. Neither outcome rewrites checkpoints, starts, amendments or lifecycle. Plain `pose close` also verifies instead of repeating the transition. An in-progress plan checks the existing amendment gate before sealing. No policy, review or historical receipt is created automatically.

### Delegated executions (`pose delegate`)

`pose review` governs the subject (bundle, brief, attestation, verify); `pose delegate` governs executions. An **agent** is a CLI profile configured in `.pose/policy/delegation.json`; a **run** is one execution; an **attempt** is a run and its continuations; a **thread** is the rounds of one scope. `pose delegate review`, `adjudicate` and `smoke` run the sealed bundle's generated brief on a disposable worktree at the sealed commit with read access only, under the attempt ledger and containment below; any other `--access` is refused. A run never records an attestation. Without `--agent` (or with `auto`) routing chooses among the agents of the purpose: first by `routing.prefer` (default `opposite-vendor-of-implementation`, in the order the policy declares its agents), then by the steps of `routing.on_unavailable` (default `same-vendor-other-model`, `wait`, `same-model`). `wait` applies only when every earlier candidate is limited with a known reset within `routing.max_wait` (default 5h) and starts the run after the first reset, without polling. The implementation routed against is the identity the bundle sealed; for a bundle sealed before bundles recorded it, the policy's `provenance.implementation`, else `--lead`. An agent named with `--agent` bypasses routing and warns when it shares the implementation's vendor. Every run records the decision (`routing`: the candidates, why each was skipped, the step taken) and `independence_achieved` (`different-vendor`, `different-model` or `same-model`); with no agent available the run does not start and the error carries the decision. `--label` names the run, `--lead <vendor>[/<model>]` declares the implementation when the bundle records none, `--dry-run` prints the resolved agent, purpose, access, working directory and argv (authorized credential values redacted) and reserves nothing, and `--json` prints one versioned document (`pose.delegate.run/v1`, `plan/v1`, `ls/v1`, `cancel/v1`, `agents/v1`, `error/v1`), usage errors included. On `ls`, `resume`, `cancel` and `agents` the same flags select: a run or an agent that does not match is not listed, or is refused when named; `--dry-run` changes nothing anywhere. Messages follow `POSE_LOCALE` (`en` or `pt-BR`). A run reference is a run id, an attempt id, a label or a session prefix of six characters or more; an ambiguous reference exits 2 and lists the candidates.

`pose delegate ls` lists attempts by their latest run with state, purpose, agent, label, turns, age and last step — for an interrupted run also its cause, whether a partial draft exists, the reset instant and the time left — and the runs in progress with the liveness of their process. `pose delegate cancel <run>` stops a run in progress; it is recorded `failed` with the cause `cancelled`, and its attempt stays consumed. `pose delegate agents` lists each agent with vendor, model, whether its CLI is on the path, the reset instant of its last recorded usage limit and the state routing reads: `available`, `limited until <instant>` (its last run hit a usage limit whose reset is ahead), `missing` (its CLI is not on the path) or `probe-failed` (its optional `probe` failed within its bound). Availability is read from the path and the recorded runs; only a configured probe runs anything. `watch` and `wait` arrive with spec `pose-delegated-review-completion-signal`, `handoff` with `pose-delegation-handoff` and `task` with `pose-delegation-task`; until then they exit 2 naming the spec. `pose review dispatch`, `resume` and `status` remain for one minor version as deprecated aliases with their behaviour and exit codes, printing the replacement on stderr.

`delegation.json` is schema 2: `agents` (vendor, model, `cli`, `events`, per-access `commands`, `effort`, `timeout`, `limit`, `session`, `resume`, `executor`, `containment`, `probe` — `command` and an optional `timeout` up to 60s, default 10s, with no placeholder), `routing` (`prefer`, `on_unavailable`, `lead_models` as `{vendor: model}` in lower case, `max_wait` up to 24h), per-purpose budgets (`purposes.<review|adjudicate|smoke|task>.max_runs_per_bundle`, `timeout`) and `env_unset`. Command templates are argv arrays; `{output}`, `{session}` and `{effort}` are whole elements, never interpolated, and `{effort}` becomes the argv fragment of the agent's effort level. An agent's own `max_runs_per_bundle` wins over the purpose's; a purpose's `timeout` wins over the agent's. `pose update` converts `reviewers.json` (schema 1) into `delegation.json` deterministically and removes it: each adapter becomes an agent whose `read` command is the adapter's command, a budget all adapters share moves to the review-path purposes, and every agent projects exactly the adapter it came from. The converted file is archived outside `.pose/policy` and named in `migrated_from`, so a run recorded before the conversion keeps its policy baseline while `delegation.json` is exactly that conversion; editing `delegation.json` ends that, as any policy change does. The engine reads `reviewers.json` while `delegation.json` is absent and refuses when both exist. A schema 1 adapter that interpolates `{output}` or `{session}` inside an argument (in `sh -c` code, for example) is not converted: `pose update` warns and keeps `reviewers.json` until the template passes the placeholder as a whole element.

```json
{
  "schema_version": 2,
  "agents": {
    "codex": {
      "vendor": "openai", "model": "gpt-6.1-sol", "cli": "codex", "events": "codex-jsonl", "timeout": "60m",
      "commands": {"read": ["codex", "exec", "-m", "gpt-6.1-sol", "{effort}", "-s", "read-only", "--json", "-o", "{output}", "-"]},
      "effort": {"default": "medium", "levels": {"medium": ["-c", "model_reasoning_effort=\"medium\""], "high": ["-c", "model_reasoning_effort=\"high\""]}}
    },
    "claude": {
      "vendor": "anthropic", "model": "claude-opus-5-5", "cli": "claude", "events": "claude-stream-json", "timeout": "60m",
      "commands": {"read": ["claude", "-p", "--model", "claude-opus-5-5", "--permission-mode", "plan", "--output-format", "stream-json", "--verbose"]}
    }
  },
  "purposes": {"review": {"max_runs_per_bundle": 3}}
}
```

The child process receives none of the parent agent's session variables (`CLAUDECODE`, `CLAUDE_CODE_*` session markers, `CODEX_THREAD_ID`, `CODEX_SESSION_ID` and the other names Claude Code and Codex set for their children), nor any name in `env_unset`, even when the containment allowlist names them; the run records the removed names in `env_removed`, never their values. An agent's `events` (`codex-jsonl`, `claude-stream-json` or `plain`) selects the parser that turns its redacted stream into normalized events — turn, message, tool call, tool output, usage limit, final message, error — kept beside the run's transcript as `<run>.events.ndjson` and bound to the record by `events_digest`. An agent that writes no `{output}` file has its draft taken from the final message its stream carries. A run in progress is known by a private marker under `.pose/review-private/active/`, which names its process the way a start lock does.

### Delegated review attempts and history

`pose delegate review|adjudicate|smoke <scope|bundle>` reserves an immutable attempt before launching the configured agent. A completed run on the unchanged bundle requires an explicit `--reason <text>` for every further dispatch, including another agent or brief kind. Quota is re-read at execution and includes failed and reserved attempts; a preview is no future authorization. Concurrent calls compete for one ordinal slot and a loser refuses without launching or retrying. Reasons are one line, at most 2048 bytes; keep secrets and session identifiers out of them.

Reservations live in `.pose/review-attempts/`, final receipts link the run, and `.pose/review-run-ledger/` witnesses exact run bytes and transcript digests. Every publication uses the exclusive synced publisher. New runs carry `ledger_version: 1`, `attempt_id` and the optional reason; legacy schema-1 runs retain their original identities, with no invented reservation or signature. An incomplete reservation, missing witness/run/transcript, inconsistent receipt, unknown record or exhausted read budget is explicitly incomplete. Inspect it; no automatic deletion, truncation, repair or retry occurs. Upgrade writers sharing these directories together. Run continuity and authenticated provenance remain separate deliveries.

`pose history-check --strict` detects missing or rewritten witnessed runs and Git modifications/deletions of tracked immutable run, ledger and attempt files, including staged or committed changes. History containing only delegated records is supported. Git/filesystem trust is required: erasing unanchored evidence and its witnesses cannot be proved from that same erased storage. No cryptographic append-only storage or vendor identity is claimed. Records are limited to 1 MiB, inventories to 10000 entries, run JSON reads to 32 MiB per operation, transcripts to 256 MiB each and 512 MiB per verification, and Git history observation to 8 MiB/30 seconds; exceeding a bound is unknown, never a clean truncated history.

`pose review verify` and MCP disclose scope-wide prior runs alongside the attestation, including earlier rejecting drafts. `pose insights` aliases `pose stats`; text, JSON, HTML and MCP `pose_insights` show runs per bundle, attempts, reruns and per-adapter declared draft approval rates. A time window limits counted events, while the full preceding history classifies reruns. Approval rate uses unambiguous completed, unsuperseded `decision: approved|changes-requested|rejected` drafts; ambiguous output, failures and stale runs are unknown. Legacy unreserved runs count as individual attempts without claiming a reservation existed. Draft labels and rates are not verified approvals and never apply an attestation or enable delegated-review automatically.

### Bound delegated adapter execution

Declare an optional `containment` object on each agent in `.pose/policy/delegation.json`. Use containment schema 1 and `trusted-process`. This backend runs a trusted local executable; a disposable worktree shares Git metadata and does not isolate filesystem, original repository, network, credential files, CPU or memory. Required guarantees that the host cannot enforce are refused before reserving an attempt or spawning a process. Linux process-group termination requires an observable process inventory and is checked after kill; descendants that escape the group remain outside its coverage. Windows/other ports do not qualify group containment from a cross-build.

```json
{
  "containment": {
    "schema_version": 1,
    "profile": "trusted-process",
    "required": ["bounded-capture", "environment-allowlist"],
    "environment": ["LANG"],
    "credentials": ["REVIEWER_API_KEY"],
    "stream_bytes": 8388608,
    "output_bytes": 65536,
    "retained_bytes": 16777216,
    "retention_ttl_seconds": 0
  }
}
```

Keep environment/credentials lists unique ignoring case (at most 128/32 names). Ambient token variables are excluded. Explicit profiles use a private disposable HOME; an omitted profile is disclosed as `legacy-trusted` and retains HOME compatibility. This is environment filtering, not protection against an executable reading same-user files. Authorize credential variable names explicitly; never put their values in policy, argv, brief or notes. Loader hooks and Git redirection variables cannot be allowlisted. Credential values and captured session references are redacted together in one bounded pass, longest match first; this is exact-value redaction, not general data-loss prevention or a guarantee against encoded secrets emitted by an untrusted adapter.

Use a positive timeout from 1ms to 24h (omitted: 60m). Omit `max_runs_per_bundle` for a finite default of three; explicit values must be 1..100, including on legacy adapters. Explicit zero/null is invalid. Omitted stream/output/retained limits are 8MiB/64KiB/16MiB; explicit ranges are 1..64MiB, 1..128KiB and 1..128MiB. Require retained bytes to cover `stream_bytes + 6*output_bytes + 1048576` for JSON escaping and metadata. The retained budget covers the run record plus transcript per execution; independent bounded ledger/proof inventories still apply. It is not an aggregate storage quota, an adapter memory quota or an OS disk limit. Memory/CPU settings, positive TTL and unknown enforcement fields are refused by this backend.

Bound setup to two minutes and 64KiB of discarded diagnostic capture; disable ambient checkout hooks. Bound concurrent stdout/stderr together during capture and read `{output}` through a root descriptor opened before spawn, refusing links, special files, identity changes and oversized files. Notes must be regular non-symlink UTF-8 files up to 16KiB. Do not interpolate brief/notes into shell code. Truncated, unsafe or unredactable channels make the execution failed/incomplete; withhold their bytes because a cutoff can split a credential. No such draft governs review authority. Caller cancellation and CLI interrupt/termination signals stop the covered process set; pipe wait is bounded.

Inspect `safety` on the immutable run, CLI dispatch/verify/resume and the existing MCP review-bundle projection. It reports profile/platform, available/unavailable capabilities, limits, capture completeness, execution cause, runtime resource identifier and the B12 cleanup OperationResult. Cleanup verifies operation ownership and removes only the captured workspace and its exact Git registration through confined descriptors, never a global Git prune. Inventory caps are 100000 workspace entries/256MiB, 1024 registration entries/256MiB and 4096 runtime entries/128MiB, depth 128. OS filesystem calls remain subject to I/O latency; no hard syscall deadline is claimed. Failure retains uncertain resources and is separate from the domain draft. It returns an operational error, blocks authority/continuation and remains an error on idempotent replay, without another spawn. Inspect the recorded runtime identifier and registration rather than rerunning the adapter to compensate.

Retain evidence without automatic expiry (`retention_ttl_seconds: 0`); newly written run/transcript files use mode 0600 and private sessions retain their existing 0700/0600 policy. Export retained redacted run/transcript, witness, attempt/continuation receipts and optional proof together, preserving inventory and digests; exclude private sessions and issuer keys. Raw-byte digests precede redaction; retained-byte digests, canonical run identity, witness and native signature follow. No retention operation removes rejection history or restores quota. Legacy records remain readable with no fabricated safety observations. No instance policy, sandbox backend or real vendor is activated by these examples.

### Continue interrupted delegated reviews

Configure optional `limit`, `session` and `resume` fields on an agent in `.pose/policy/delegation.json`. Use RE2 patterns; session/reset patterns need exactly one capture group. Recognize limits by declared exit codes or output patterns in stdout/stderr or `{output}`. Parse reset captures as RFC3339 instants. The engine does not infer vendor vocabulary. Example fields on an otherwise configured agent:

```json
{
  "limit": {"exit_codes": [75], "output_patterns": ["LIMIT"], "reset_pattern": "reset: (\\S+)"},
  "session": {"pattern": "session: (\\S+)"},
  "resume": {"command": ["reviewer", "resume", "{session}", "--output", "{output}"], "max_resumes": 3, "max_wall_time": "60m"}
}
```

Pass `{session}` as an entire argv element, never inside shell code. Captures from both output channels must agree. Session references are saved under `.pose/review-private/` (directory 0700/files 0600, self-ignored by Git); keep that runtime material private. Public records contain the session digest. The supervisor redacts the captured reference from both transcript and draft before publishing; ambiguous captures withhold the unredacted bytes. Losing private material makes a run not recoverable; no replacement session is invented.

Run `pose delegate ls [--json]` to inspect interruptions, whether a partial draft exists, reset instants and remaining wait. `pose doctor` warns about interrupted attempt endpoints. Runs finish completed, failed or interrupted; legacy stale records remain readable. Undeclared interruptions are unknown and not resumable. An interrupted draft is partial evidence, never a rejection or a review.

Run `pose delegate resume <run>` (`--dry-run` previews it; repeating it returns the recorded continuation) to continue with the same agent, captured session, brief digest, sealed commit and reconstructed checkout digest. Resume uses the original attempt and does not spend another attempt quota. The default maximum is three resumes and 60 minutes of accumulated wall-clock; configure `resume.max_resumes`/`max_wall_time` to change these bounds. Policy changes, changed inputs, lost or rewritten predecessors, terminal predecessors and spent budgets refuse. An immutable predecessor claim permits only one continuation; repeated requests return the recorded result or expose its pending reservation without launching another process. A lost host before a result is published remains explicit incomplete evidence; this is not automatic recovery without a captured interrupted record.

Use `--wait-until-reset[=<duration>]` to wait once for a recorded reset, plus at most one second of jitter, then revalidate and resume. Default and maximum wait are 24 hours; a missing or more distant reset refuses. No vendor polling or automatic fallback occurs. To choose another agent after a pending usage limit, run it explicitly with `--agent <name>`; this creates a new attempt with `limit-of:<run>` and discloses both runs. Insights reports resumes separately from attempts and reruns; declared draft approval rates use completed unsuperseded drafts only.

### Verify signed delegated run provenance

Declare the executor and implementation baseline before dispatch. A bundle that records its implementation identity is compared with that identity: `provenance.implementation` is read only for bundles sealed before bundles recorded it, and a dispatch warns when the policy still declares it for a later bundle. Add `provenance` to the delegation policy and an `executor` agent principal to every agent. A schema 1 policy takes the same fields on its adapters, as below. The following identities are synthetic examples; record the real declared baseline rather than inferring it from a reviewer name:

Attach `--run <run-id> --run-proof <proof-id> --sign <issuer>` to a complete `pose review attest` request. The native issuer derives authority principal/execution bindings from the run and signs the exact reference. Criteria, tools, evidence and all ordinary preflight checks still apply. A rejecting or ambiguous draft cannot support an approval; a run-backed attestation cannot predate its completed run or signed proof. Adjudication/smoke run proofs bind their kinds but cannot be used as review attestations. Automatic validation/application of complete typed conclusions belongs to the capability, not to run signing.

Non-adopting instances keep declared behavior. A machine run never satisfies mandatory-human. Catalog adoption, cutoffs/rollback and automatic conclusion application remain separate capability work.

Current issuer pins, project/audience/time, sealed inputs, retained artifacts and original/continuation receipts are reverified. Revocation, missing receipts, rewritten data or stale inputs remove machine assurance. Signing does not reset quotas or erase earlier rejecting runs. Worktree binding currently requires the originating local context; no portable remote-runner trust or universal containment is claimed.

# Git state that cannot be read is unknown, and a worktree is judged by its content

## Context

Spec `pose-git-and-dispatch-snapshot-integrity` (B07; front 2 D02, T3-02 and CONS-03).
Three places turned a failure to read Git into a fact:

- `ungeneratedChanges` returned no changes when `git status` failed, so the close plan
  sealed evidence over a tree it could not see.
- `RunReviewDispatch` ignored the error of `git status` and of `rev-parse HEAD` in the
  review worktree, and judged the run by `git status --porcelain` text: a path made
  `assume-unchanged` or `skip-worktree` by the reviewer, a link, or a quoted name could
  hide an edit; a rename was split on the text ` -> `.
- Any file under `.pose/indexes/`, `.pose/results/` or `.pose/review-bundles/` was
  "derived", so a review could rewrite the validation matrix or sealed evidence and still
  pass.

## Decision

D1. Reading Git state has three outcomes, not two: a known state, `ErrGitUnavailable` (the
directory is not a repository at all; exported trees and fixtures) and `ErrGitUnknown`
(a repository whose status, HEAD or tree could not be read). The last is never clean: the
close plan blocks, and the snapshot and path checks report "unknown". A damaged repository
says "not a git repository" like a missing one, so the two are told apart by the presence
of a `.git` entry, not by the message.

D2. The review worktree is judged by content, not by Git's account of it:
`WorktreeDivergence` compares every file of the sealed commit's tree (blob id, link target,
executable bit) with the file on disk, and lists untracked and index-only files Git does
not ignore. Paths are read with `-z`, never quoted text.

D3. Derived regeneration is a list of what each producer writes, with a `tracked` rule:
existing sealed records are never rewritten, new ones are written. The validation matrix
and the policy are not regenerated by a review.

D4. A run that finishes after its bundle was superseded or changed, or its policy changed,
is recorded `stale`: it stays as history, and no consumer reads it as the scope's current
fulfilment. A commit that touches none of the sealed inputs does not invalidate a run.

## Consequences

- **Stricter, classified minor.** A dispatch that passed over a hidden edit, or over a change
  to the validation matrix, now fails; the close plan blocks on an unreadable repository.
- Compatibility: read-only projections retain their exported-tree fallback. Execution
  snapshots require readable Git metadata and cannot use that fallback.
- Reconciled 2026-10-20: compare materialization before and after execution, including
  ignored files in the disposable worktree; validate origin, policy and bundle again
  before effects. Bound observations to 100,000 entries and 256 MiB. Adapter output
  belongs outside the worktree; derived-directory names grant no write permission.
- Limits: these observations do not isolate the adapter (the adapter-containment
  contract), nor detect an edit restored between observations.

## Falsifier

This decision is wrong if a repository whose status cannot be read is reported clean, if an
edit hidden with `assume-unchanged`, `skip-worktree`, a link or a renamed path passes a
dispatch, if a review can rewrite the validation matrix, the policy or a sealed record and
still complete, or if a commit that touches no sealed input invalidates a run.
`git_snapshot_integrity_test.go` in `internal/pose` and `internal/cli` asserts each of these.
